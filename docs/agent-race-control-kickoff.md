# Agent Race Control — Kickoff Brief

You are helping me build a small, focused desktop app from scratch. Read this whole brief first, then **restate the plan and your assumptions back to me and wait for my confirmation before writing any code.** Work in phases; pause for my sign-off at the end of each phase.

## What we're building

**Agent Race Control** (package/repo slug: `agent-race-control`) is a session-aware terminal cockpit for Claude Code on **native Windows** — **Windows first, macOS in progress** since 2026-09-12 (see *macOS: Windows first, macOS in progress*).

The problem it solves is concrete: I run several Claude Code sessions at once, each in its own terminal window — plus more terminals for `npm run dev`, builds, and the like — and I waste time hunting the Windows taskbar for the right one. Agent Race Control consolidates **all of it** into **one window, one taskbar icon**: every Claude Code session *and* the plain shells I run alongside them. An overview I can glance at and a terminal I can drive, together. If a terminal is open, it lives in Agent Race Control.

## Non-negotiable ethos: minimal

Minimalism is a hard requirement, not a preference. I evaluated the existing tools (Kanban Code, Nimbalyst, claude-code-kanban, and others) and rejected them as bloated. The bloat was never the embedded terminals — it was everything bolted around them. **Agent Race Control is Windows Terminal, except each tab knows whether it's a Claude Code session — and shows its name, color, and status — or a plain shell. Nothing more.**

### Explicitly OUT of scope (do not build these, and flag me if you're tempted)
- No git worktree or branch *management* — I have git. (Read-only **display** of the current branch/worktree is in scope — pure observability, like status-from-hooks; see "Branch/worktree tree" below. We never create, switch, or delete anything. The one arm's-length exception, settled 2026-07-19: the repo card can spawn a Claude with `--worktree <name>` — **Claude Code** creates the worktree at spawn and removes it at exit; the app still executes zero git write commands. See *Worktree workflow*.)
- No PR / GitHub integration.
- No kanban columns or drag-and-drop.
- No task-dependency graphs.
- No theme gallery — one clean look. (A **light / dark / system** appearance toggle is in scope; a gallery of decorative themes is not.)
- No database — small JSON files for local state, nothing heavier.

Every "wouldn't it be nice" gets checked against this list. When in doubt, leave it out and ask.

## Non-negotiable ethos: full-fidelity Claude Code

Agent Race Control must run the **unmodified `claude` CLI in a real pseudo-terminal** — it does not wrap, proxy, embed via SDK/headless mode, or reimplement Claude Code. This is the single most important design constraint, and it's *why* Agent Race Control exists: a real PTY session is indistinguishable from launching `claude` in Windows Terminal, so **every feature the terminal has is present by construction** — remote control, rewind/checkpoints, `--resume`, slash commands (including `/btw` side questions and their overlay keys), **background agents and the agent view** (left-arrow detach/switch, `/attach`, `claude agents` — discovery is file-based under `~/.claude/jobs/` + a per-user supervisor daemon, so it's launch-method-agnostic), plan mode, hooks, MCP, mouse and keyboard interaction, true color, hyperlinks — all of it, 100% identical.

Other tools (Kanban Code, the Claude desktop app, GitKraken Kepler, etc.) integrate Claude Code through the SDK, headless mode, or a non-TTY wrapper, so those interactive features are missing or degraded. Agent Race Control deliberately does **not** do that. The burden on us is therefore inverted: our job is to **not interfere**. Concretely:

- Spawn the real `claude` binary in a real PTY (ConPTY via `node-pty`); never intercept, rewrite, or filter the byte stream in either direction.
- Pass **all keystrokes** straight through to the PTY — including chord/escape sequences Agent Race Control might otherwise want (e.g. Esc-Esc for rewind, Ctrl+C, Ctrl+R). App-level shortcuts must not shadow anything Claude Code uses.
- **Zero new muscle memory.** Inside the terminal, Agent Race Control invents no shortcuts of its own — it follows stock Windows Terminal conventions (e.g. Ctrl+Shift+C/V and right-click for copy/paste; Ctrl+C is Claude's interrupt, untouched; **Ctrl+= / Ctrl+- / Ctrl+0 zoom the window** — the same keys Windows Terminal and VS Code bind, consciously shadowing the rare readline undo chord). Moving between Agent Race Control and a regular terminal must require no change in habits, in either direction.
- Pass through the full environment, a correct `TERM` (`xterm-256color`), accurate rows/cols on every resize, clipboard copy/paste, and OSC-8 hyperlinks. One deliberate carve-out: strip the env vars an enclosing Claude Code session injects into its children (`CLAUDECODE`, `CLAUDE_CODE_SESSION_ID`, …) — fidelity means matching a *fresh terminal*, not the launcher's ancestry, and leaked markers make spawned claudes act as nested child sessions (which silently disables transcript persistence — no resume). Found the hard way.
- Dropping a file on the terminal pastes its quoted path at the cursor — the same bytes Windows Terminal sends, and how images/files get handed to Claude Code in a terminal. (The window itself never navigates: `will-navigate` is blocked.)
- Never steer Claude Code's appearance: no `COLORFGBG`, theme flags, or config injection. Agent Race Control's light/dark toggle themes Agent Race Control's chrome only (see *Appearance*). Claude Code picks its own theme.
- If a feature works in Windows Terminal but not in Agent Race Control, that's a bug in Agent Race Control — not a feature we chose to omit.

## Layout

- **Timing tower (left):** a list of every session showing its name, a color dot, and a status indicator. Named after the F1 broadcast graphic it copies — the left-edge column of drivers with position and status; "tower" in code and shorthand.
- **Right pane:** one terminal, showing whichever session I clicked in the tower.
- The tower is the overview; the pane is the cockpit. Same window. Glance to find, click to drive.
- **Row click always hands the keyboard to the terminal (fixed 2026-07-19):** clicking a session row re-asserts xterm focus even when the row was *already* focused — a dismissed menu or chrome input otherwise kept the keyboard, and "click to drive" silently didn't. Terminal's focus effect only re-ran when `active` changed, so the row click bumps a **focus epoch** the effect also reads. Companion fix, required for safety: the **rename input** swaps `autofocus` for the explicit focus-on-mount action (the attribute is not honored on dynamically inserted inputs — verified empirically on the worktree name field), because with row clicks now grabbing terminal focus, a rename field that silently failed to take focus would have sent the typed name into the live session.
- Visual reference: **the F1 timing tower** — a column of colored entries with names and live status, the whole race readable at a glance; click one to go on board.
- **Status dot colors (settled 2026-07-12, replacing CI-badge semantics):** traffic lights read from the **user's** point of view — every color answers "is this session mine to act on?" Claude sessions: **running = red** (the agent is driving, hands off), **waiting = amber, pulsing** (it's asking for you), **idle = green** (your turn — a fresh session starts here, at its prompt). **A live shell is neutral full-strength ink (`fg`)** — a power LED, not an agent state: "running" only means its PTY is alive (we can't and won't inspect the foreground process), and green stays exclusive to "a Claude awaits you". **exited = faded muted gray** for both types — a shell's dot literally just dims when it dies. All hexes are existing Primer tokens (`danger`/`attention`/`success`/`fg`) with roles remapped — zero new colors. **Light-theme refinement (2026-07-14):** the dots use the brighter Primer *.emphasis* mid-tones on light (`success` #2da44e, `attention` #bf8700) instead of the *.fg* text tones (#1a7f37/#9a6700), which read muddy as small filled dots on white; `danger` is unchanged (.fg == .emphasis == #cf222e) and dark keeps its already-bright .fg tones. Accepted trade-offs: a tower of busy agents glows red (correct under this framing — all stop lights, nothing for you), and red is spent on "busy", so a hypothetical bad-exit state can never claim it (fine — don't over-model status). **Status RGB setting (2026-07-15):** a toggle (Settings menu, **off by default** as shipped, **on by default since 2026-09-12**) that recolors the three agent-status dots to pure traffic-light RGB — running `#ff0000`, waiting `#ffaa00`, idle `#00ff00` — identical in both themes. The Primer-token defaults above are unchanged; this is a single named switch for people who want literal traffic-light hues, not per-color customization (the shell power-LED, exited-gray, and the close/clear hovers all keep reading the palette tokens). Persisted as `statusRgb` in the state JSON. Scoped in code to dedicated `--dot-running/waiting/idle` CSS vars fed by the `dots` derived in `App.svelte`.
- **TODO marker (issue #3, 2026-07-17):** a cosmetic per-session "revisit later" flag overlaid on the status dot, **both session types**. The dot becomes a small `<button>` (mirrors the close-button pattern — native button, `stopPropagation`); **left-click toggles TODO, toggle-only — it does not focus the row** (a dedicated control; click elsewhere on the row to focus). While on, the dot pulses blue regardless of the underlying status color (reuses the existing `pulse` keyframe), riding the same Status RGB toggle as the status dots: the **theme accent** (`palette.chrome.accent` — #0969da light / #2f81f7 dark) by default, **pure `#0000FF`** when Status RGB is on (matching the pure-RGB traffic lights). Fed via a `--dot-todo` var off the `dots` derived. It **auto-clears the next time the underlying status changes color**: every status write (hooks `applyStatus`, the keystroke nudge, exit) funnels through one `setStatus(session, next)` that drops TODO on a value change — each status is a distinct color, so a value change *is* a color change; a *running* session flagged TODO therefore clears the moment it finishes (running→idle). Clicking again clears it manually and the dot returns to its live status color (`session.status` is tracked underneath the whole time, so there's no "previous state" to restore). Persisted as `todo` per session in the state JSON (additive/optional) so it **survives restart** — set directly on restore, *not* via `setStatus`, so a relaunch's status defaults don't count as the clearing change. **Ethos:** cosmetic only — no effect on sorting, focus, spawn, resume, or any logic. It reuses the existing dot (no new UI element) and carries no columns/workflow-states/ordering, so the "no kanban" line holds — a sticky note, not a board.
- **Two more display toggles — Status dot / Color title glyph (2026-08-27):** both live beside Status RGB in the Settings menu, persisted additively (`statusDot`, `glyphColor`). **Status dot** is **on by default** (absent in the state file reads as *true*) — it was the only toggle that was, until the 2026-09-12 re-baseline: off, the session rows and the collapsed cards' roll-up dot render without it and the shared row grid's dot track collapses to 0px (one `--dot-track` var, so branch rows and titles stay aligned) — the rows go text-only, which also takes the **TODO flag with it**, the dot being its only affordance (accepted: it's the same switch that hides the thing TODO paints on). **Color title glyph** (**on by default since 2026-09-12**, off as shipped) paints the *leading glyph of the row's title* — the tower shows the title verbatim, spinner churn included, so Claude's own frame is already there to color: **star/asterisk family green, circle/half-circle family red**. The glyph alone picks the color; it reads **nothing** from `session.status` and borrows **none** of the `--dot-*` palette (Status RGB doesn't reach it), using the Primer `--success`/`--danger` ink so it stays theme-aware. Classification is `glyphLead` in `sessions.svelte.ts` (unit-tested): the **first** character picks the family and the run of same-family characters after it paints with it (a multi-frame lead is one glyph, not half-colored); everything else — braille spinner frames, shell titles, user labels — classifies as null and keeps the row's own ink. Deliberately literal to the two families named: the braille frames are a busy signal too, but they were not part of the ask and coloring them is a one-line extension if they ever earn it.

### Directory groups (derived, not managed)
- Sessions group by their **working directory** — the group *is* the dir. It appears with its first session, disappears with its last; the header shows the dir basename (parent path muted, full path on hover). No create/rename/delete surface at all.
- **Header anatomy (settled 2026-07, replacing the tinted path pill):** the directory color renders as an F1-style **team stripe** — a 3px vertical bar at the header's left edge. Icon and basename stay muted; the parent path is plain muted text on the right, no pill. The pill was retired because it made the least important info in the row (the parent path) the loudest element in it.
- **Header actions:** hovering the header swaps the path text for a right-aligned **segmented cluster** of three outlined buttons — new Claude (✳), new shell (⌨), and Show in Explorer (same `shell.openPath` verb and label as the session context menu). One bordered control, not floating glyphs.
- **Newest first within a row (2026-09-05):** a spawned session is inserted at the **top** of its directory's list, not appended to the bottom — the one you just spawned is the one you're about to drive, so it belongs where your eye already is. The tower renders a row by filtering the session array on an exact cwd match, so "before the first session sharing this cwd" *is* the top of that row, and every other row's order is untouched. **Duplicate keeps its own rule** — directly under its source, Windows Terminal's "Duplicate tab" placement — because that action is *about* the row it clones. Restore is unchanged too: it replays the saved order verbatim, so this is where new rows *enter*, not a sort.
- **Drag & drop:** the whole card is the group's drag handle, reordering groups (order persisted as `dirOrder`); sessions reorder *within* their group only — a session's directory is a fact of the running process, not a label to move.
- This replaced v1's manual folders: derived truth beats managed state, and it deleted three functions and two UI affordances. Boundary otherwise unchanged: no kanban semantics, no per-group behavior. (The one blessed nesting exception is the branch/worktree tree below — recorded there.)

### Repo cards (issue #5 — grouping settled 2026-07-17, card presentation settled 2026-07-19)
Every group renders as a **card**: a faint **wash** of its colour (8% over the tower bg) with a 2px colour **tab welded to the card's left edge**, laid out on a **12-column grid** so markers, titles, dots, icons and names align to fixed tracks. A **git repo** card nests **repo → branch → sessions** (the one blessed exception to the otherwise-flat "no nesting" rule — running parallel agents across a repo's worktrees is the app's core use case); a non-git folder card is just title → sessions. This is pure observation (see the qualified out-of-scope line above — we display the branch, never manage it). The card presentation **supersedes** the earlier F1-stripe/tree look (edge stripe + a 1px repo-colour trunk + 12px branch tabs), chosen over ~20 playground iterations; the *grouping* model is unchanged.
- **12-column grid (`repeat(12, 1fr)` per row — tracks align across rows without subgrid, since every row is the same width):** col 1 = the repo **title** (marker `none-left`: the repo name is a flush-left heading, no icon) + the branch icon; col 2 = branch names + session dots (both flush-left → one clean vertical edge); col 3 = session type icon; col 4+ = session name. **Default card spec (playground-tuned, kept in memory):** wash 8% · edge tab 2px · no border · radius 2px · marker none-left · icon 12px · fonts title/branch/session = 14/12/12.
- **Grouping = Model B:** the top group is the **repo**, keyed on its *shared* git dir so **every worktree of one repo groups under one card**. `git rev-parse --path-format=absolute --git-common-dir` returns the same absolute `<repo>/.git` from every worktree (verified empirically against a real linked worktree, git 2.54); `dirname` → the repo root, basename → the repo name. Each branch row is a **cwd**; its branch (`--abbrev-ref HEAD`) labels the row, with `→ <worktree-basename>` shown when the worktree dir differs from the repo name. **Detached HEAD** (`--abbrev-ref` → `HEAD`) shows a short SHA (`--short HEAD`, a second call — `--abbrev-ref` is a sticky rev-parse mode).
- **Git info is the app's first (and only) git subprocess.** `src/main/git.ts` — `getGitInfo(cwd)` via `execFile('git', …, { timeout })`, **fail-open**: any error/timeout → `{ isRepo: false }`, never a throw or hang. Exposed as `window.arc.git.info(cwd)`; cached per cwd in the renderer (`gitInfo`, not persisted — recomputed on load and on **window focus** so a `git checkout` in a shell updates the card; no `.git/HEAD` fs-watch). A non-git cwd (or info not yet landed) renders as a plain card until it resolves.
- **Ordering reuses `dirOrder`** (a list of cwds — no schema bump): cards are *derived* by clustering cwds by repo in first-appearance order (`groupCwds`, unit-tested). DnD — the **whole card** is the group's drag handle, moving its cwd block (`moveGroup`); **sessions** reorder within their cwd (their row stops `dragstart` from bubbling so a row reorder can't become a card move). No branch-level DnD.
- **Drop feedback (settled 2026-07-19):** a group drop previews as a **2px accent insertion line floating in the margin gap** where the card will land — above the hovered card (*before*) or below it (*after*), chosen by which half of the card the pointer is over — instead of highlighting the whole target. It's a `::after` in the gap, so the card is `overflow: visible` and the colour tab rounds its own left corners to stay clipped. "After a card" resolves to "before the next **visible** card": the DOM is the source of visible order (hidden groups aren't rendered), so the hovered card's next `.card` sibling is it, and `null` → append — which is how a card reaches the very top or bottom. Mid-drag the card's inner content drops `pointer-events` (keyed off `data-dragging` on the tower body) so native DnD's per-child `dragenter`/`dragleave` and `:hover` can't flicker the line or light up card chrome as the cursor crosses the target.
- **Colour = the repo's primary (first-in-order) worktree's colour** — drives the card wash + edge tab (no `dirColors` re-keying). Right-click the card title to recolor; `setGroupColor` writes *every* worktree so it stays stable as the primary changes.
- **Branch state (settled 2026-07-19):** each branch row answers "is this feature safe to merge/close?" at a glance — a muted **`●` when the worktree has uncommitted/untracked changes** and **`↑n ↓n` ahead/behind counts**, rendered after the branch name in plain muted ink (deliberately NOT the traffic-light colors — those stay reserved for session dots; full wording in the row tooltip). The comparison base: the branch's **upstream** when set (so `main` reads as push/pull), else the **default base** — **local `main`/`master` first, then a verified `origin/HEAD`** (local-first is deliberate: ahead-of-local-main answers "merged yet? safe to delete?" in a merge-locally workflow, where origin/HEAD would inflate a feature's count with main's own unpushed commits and keep it reading ahead after a local merge; origin/HEAD covers repos whose default branch has another name, and a dangling symref is verified before trust). Never the branch itself. A `worktree-<name>` feature thus reads as *unmerged work* (↑, don't delete the branch) and *needs rebase* (↓). Data rides the existing `getGitInfo` pipe: one `git status --porcelain=v2 --branch` (header → upstream ahead/behind; any entry line → dirty; the parser is pure + unit-tested) plus at most one `rev-list --left-right --count base...HEAD`, all fail-open per-field with the same 3s timeout. **Refresh cadence — no polling:** the existing on-focus + first-touch refresh, plus a status-driven one: a session transitioning to **idle** (a turn just ended — files likely changed, and idle is exactly when "safe to merge?" gets asked) re-reads its cwd via the `setStatus` choke point. Deliberately NOT on `exited` — post-cleanup the worktree dir is gone and a refresh would flip the row into a plain-folder card. Synthetic parked rows show no state (nothing to observe yet).
- **Collapse (settled 2026-07-19):** clicking a card's **name** folds it to just its title (branch + session rows hidden) and unfolds it — a *click*, not a drag, so dragging the card to reorder and right-click-to-recolour both still work on the same title. A collapsed card leads its title with a **roll-up status dot** so a folded card still reads at a glance, most-urgent first: **waiting** (a session wants you) › a running **Claude** (agent driving) › any other **running** (a live shell) › **idle** › **exited** — it carries the winning session's type, so a lone running shell reads neutral (`plain`), never red, the same per-type colours and waiting-pulse the rows use. Collapsed state is **per group key**, persisted as `collapsed` (a list of keys — additive/optional, filtered to alive groups on save, mirroring `dirColors`); default expanded. This ships the previously-deferred collapse + roll-up; the once-floated *roll-up-on-an-expanded-title* is dropped — expanded cards show their real per-session dots.

### Worktree workflow — a feature is a worktree (settled 2026-07-19)
The multi-repo model on top of the repo cards: **repo = card, feature = worktree (one branch row), sessions = rows under it** — parallel features are parallel worktrees, and the tower's statuses tell you which feature wants you. The app's contribution is deliberately one affordance plus plumbing; **Claude Code itself is the worktree manager** (creation at spawn, removal at exit), so the out-of-scope line above stays literally true of the app.

- **The affordance:** the repo card title's hover cluster gains a **new-worktree button** (`create_new_folder`) that swaps the title for an inline name field — **Enter spawns, Escape/blur cancels** (creating a branch is a real side effect; a stray click-away must not spawn). The name is slugified (spaces→dashes, quotes dropped); **blank lets Claude auto-name**. Spawn is the normal Claude spawn plus `--worktree <name>`, cwd = the repo root (the main checkout — `--worktree` anchors `.claude/worktrees/` there).
- **What `claude --worktree <name>` does (all verified empirically 2026-07-19, v2.1.215, live probes):** creates `<repo>/.claude/worktrees/<name>/` on a new branch `worktree-<name>` and starts the session inside it, worktree locked while the session lives (`locked claude session <name> (pid …)`); the session takes the worktree's name. **No dependency install** — the worktree is a bare checkout (official docs: ask Claude to install, or automate via a personal `WorktreeCreate` hook). Composes with our pinned `--session-id`: the transcript lands at `~/.claude/projects/<worktree-cwd-encoded>/<uuid>.jsonl` — exactly the resume/preview contract. On `/exit` with nothing pending the worktree is **auto-removed** ("Cleaning up worktree (no pending changes)…", no prompt); with work pending Claude prompts keep/remove in our own pane. **The branch always survives removal** — deletion is the user's (`git branch -d`, or ask Claude before exiting). A crash or `claude -p` leaves the worktree behind, locked. Docs-only facts: the branch bases on the **default branch**; reusing a name **reopens** that worktree; `.worktreeinclude` copies gitignored files (`.env`…) into new worktrees. **Trust gate:** `--worktree` errors in a never-trusted repo ("Workspace trust not yet accepted…") — one plain `claude` run per repo clears it permanently; the error renders in the pane, which is the correct surface.
- **cwd follows the hooks:** a `--worktree` spawn's PTY starts at the repo root, but the session lives in the worktree — and every hook payload carries the session's real `cwd`, so the status server forwards it and `applyStatus` **adopts a diverged cwd** (same observation channel as status; the spawn-echo sibling is `applySpawnCwd`, the conversation-id sibling is the issue-#2 `/clear` follow). The reactive cwd re-groups the tower row under its new branch row, and the existing machinery re-points the rest by construction: Preview's arm effect re-runs on a cwd change, and main's `transcript:watch` already disposes/recreates a tail whose path changed (reset protocol dedupes).
- **The row parks on its branch row from the start (settled 2026-07-19, follow-up):** waiting for the first prompt to re-group read as the row being in the wrong place, so a named `--worktree` spawn now shows a **synthetic branch row immediately** — `worktree-<name> → <name>`, appended after the real rows, built in the tower derivation from the session's pending `spawnWorktree` flag. This displays the **app's own intent** (it typed the flag itself), not a guess about Claude's state; the hooks stay authoritative — the first payload's cwd adopts, clears `spawnWorktree`, and the real branch row takes over under the same label (dirOrder appends, so placement doesn't jump). `spawnWorktree` is **persisted while pending** (additive key): a parked, never-prompted session survives restart, re-spawns with `--worktree <name>` (reopen semantics — probe-verified safe), and keeps its parked row; adoption clears the flag so an established session never re-passes it. The reopen menu filters by each session's *target* cwd (`sessionTargetCwd`), so a worktree mid-reopen isn't offered twice. **Blank auto-named spawns can't park** (the name is unknown until Claude picks it) — they sit on the root row until the first prompt, and the pending flag deliberately isn't persisted for them (restoring '' would mint a second random worktree; the orphan stays visible in the reopen menu instead).
- **Reopen menu (settled 2026-07-19, later the same day):** a parked worktree — kept at `/exit`, stranded by a crash/×, or made by hand — has no session, so it was invisible in the tower; the designed park-a-feature flow dead-ended in remembering names. The repo card title's cluster gains a **history button** opening a menu of the repo's worktrees that currently show no rows (`listWorktrees` in git.ts — `git worktree list --porcelain`, read-only, fail-open, fetched on click; `parkedWorktrees` filters out the main checkout and any cwd with sessions). Picking one spawns a Claude back into it: a `.claude/worktrees/<name>` path goes through `--worktree <name>` so Claude re-attaches its cleanup lifecycle (`worktreeSpawnName` decides); any other worktree gets a plain spawn in its directory. **Probe-verified before building (v2.1.215):** reopening by name preserves committed work; the docs' "a clean worktree may reset to the default branch" did NOT manifest (a clean unmodified worktree stayed on its base even after main advanced — re-verify if a Claude update changes this); a stale lock from a dead session doesn't block reopening. Scope guard: the menu reopens, full stop — no delete/prune actions (that's the worktree-manager panel the out-of-scope list forbids); removal stays Claude's exit flow and git's.
- **No resume into thin air:** a requested cwd that no longer exists at spawn is now an **error in the pane** (row exits), replacing the old silent home-dir fallback — a cleaned-up worktree (or any deleted folder) must be a visible fact, not a session quietly running somewhere else. Restored worktree sessions otherwise resume normally: transcripts live under the worktree cwd, so `--resume` in that cwd continues mid-feature.
- **Deliberately NOT built** (checked against the out-of-scope list): no worktree manager panel, no branch picker, no sync/merge/PR buttons, no branch deletion, no app-run `npm install`. Cleanup UX is Claude Code's own exit flow rendering in our terminal; sync (`git fetch && git rebase origin/main`) and branch surgery are git in a shell row or a sentence to the session's Claude.
- **User-side setup (config, not app code):** gitignore `.claude/worktrees/` per repo (this repo's own `.gitignore` gained it); `.worktreeinclude` for env files; optionally a `WorktreeCreate` hook in `~/.claude/settings.json` for auto-`npm install` (the app never touches `~/.claude`). pnpm makes per-worktree installs hardlink-cheap if they sting.
- **Developing *this* app in a worktree needs `ARC_USERDATA` (found 2026-09-05):** two `npm run dev` runs from two worktrees of this repo fight over the **single-instance lock**, whose identity is the userData dir — and `productName` is `Agent Race Control` in every checkout, so both resolve to the one `%APPDATA%\Agent Race Control`. Whoever starts **second** hits `!gotLock` and calls `app.quit()` (`src/main/index.ts:21`). The failure is near-invisible: the loser builds fine, sidesteps the port clash (`Port 5173 is in use, trying another one...` → 5174), prints `starting electron app...`, then `electron-vite dev` follows its electron child out with **exit code 0 and no error message** — measured at **2s**, which reads as "the dev server shuts down after a few seconds" rather than as a lock collision. Nothing is being *closed*: the second instance refuses to start, so the symptom lands on whichever agent launched last. The fix is config, not code — the existing dev-only deviation already covers it, since `ARC_USERDATA` is read *before* the lock precisely so two instances can coexist:
  ```bash
  ARC_USERDATA=<worktree>/.dev-profile npm run dev
  ```
  Worth doing even when only one app runs at a time: a shared userData also means a worktree's app reads and writes **the real tower's state JSON** — session list, groups, colours, zoom — so an experimental build (say, one adding a new session kind) can persist state the main checkout then loads. Per-worktree profiles keep that blast radius at zero. **The gitignore is not automatic — corrected 2026-09-05 after agent-codex flagged it:** `.claude/worktrees/` only hides that path from the *main checkout's* index; inside a linked worktree the worktree root **is** the repo root, so a `.dev-profile/` there is matched against the same `.gitignore` as any other top-level dir and that pattern doesn't reach it. `.gitignore` therefore gained **`.dev-profile/`** next to `.screenshot-profile/`, which covers the documented path from every checkout. (It was in fact already excluded on this machine via `.git/info/exclude` — a line left from the 2026-08-12 status-signal probes — but that file is untracked and machine-local, so it would not survive a fresh clone and is invisible to anyone reading this note. Tracked pattern, not local luck.)
- **Which side sets it (the daily shape of this):** the intended workflow is *using* the real app while a worktree agent improves it, so **the real app keeps the default profile and the worktree sets `ARC_USERDATA`** — never the reverse. That way the tower you actually work in keeps its sessions, groups and colours at the untouched `%APPDATA%\Agent Race Control`, and the experimental build gets a throwaway tower that starts empty and can be deleted without consequence. **Verified empirically 2026-09-05:** two `npm run dev` instances — main checkout and the codex worktree, distinct `ARC_USERDATA` paths — ran side by side, each building and running its own `out/main` bundle, both alive with no lock contention. Only the *shared* userData collides; the lock is per-profile, exactly as the screenshot harness already relies on.

### Two session types
- **Claude session** — bash that `exec`s straight into `claude` (see spawn spec below). The PTY *is* the Claude process: when claude exits, the session is exited. Full status set.
- **Shell session** — a plain interactive Git Bash, for `npm run dev`, builds, git, or anything else. This is what makes Agent Race Control the *only* terminal window I need — without it I'd still have stray terminals on the taskbar, defeating the point. Status is `running`/`exited` only.
- Both types live in the same tower, same look: name, color dot, status. New-session UI offers exactly these two choices. A shell session is not a degraded Claude session — it's a first-class terminal.

### Appearance (light / dark / system)
- Three modes only: **System** (follow the OS), **Light**, **Dark** — **Dark is the default since 2026-09-12** (it was System; see the defaults entry below). This is a single appearance toggle, not a theme gallery.
- Use the **GitHub themes**: **GitHub Light** (`github-light-default`) for light, **GitHub Dark** (`github-dark-default`) for dark. Pull the exact hex values from GitHub's Primer primitives when implementing — don't trust memory for the palette.
- **One black surface, untinted greys — dark only (2026-09-11):** the one deliberate deviation from Primer, and it applies to **dark alone**; light is untouched Primer (its canvas was already `#ffffff`, its `bgSubtle` still `#f6f8fa`). Two parts. (1) **Dark has a single surface and it is true black** — `bg` *and* `bgSubtle` are both **`#000000`**, not GitHub dark's `#0d1117`/`#161b22`. There is **no raised plate**: the tower, the menus and the Settings panel share one ground with the terminal, and surfaces are told apart by their **border**, never by a fill. An all-day terminal cockpit wants the deepest ground, and on OLED the black is free. (An interim `#111111` plate was tried and dropped — a step in value only still read as a grey plate.) (2) Every remaining dark neutral is **re-derived as a true grey**: Primer's dark scale is uniformly blue-shifted, which tinted the whole chrome, so `border` `#30363d`→**`#353535`**, `fgMuted` `#7d8590`→**`#848484`**, `fg` `#e6edf3`→**`#ececec`**, each computed at the **same relative luminance** with R=G=B (the value structure stays Primer's; only the cast goes). The xterm `background`/`foreground`/`cursorAccent` and the three scrollbar-slider tones follow the same tokens.
  - **What deliberately keeps a hue:** the `accent`, the `success`/`attention`/`danger` status tones, the selection wash, `DOT_COLORS`, the per-directory card tint (`--dir-color` mixed over `bgSubtle` in `App.svelte`), and **all 16 ANSI slots** — those are the CLI's colors, not the chrome's, so the de-tint stops at the terminal's edge. Colour in dark is earned, never ambient.
  - **Consequence — every hover fill paints with `border`, never `bgSubtle`.** `.row`/`.icon-btn`/`.spawn-btn` always did; `.menu-item` and `.settings-close` were moved onto it here, because a subtle fill is literally invisible once `bgSubtle === bg`. One idiom now, and any new hover follows it. The five *bordered* subtle surfaces (`.chip.active`, `.segmented`, `.switch`, `.picker`, `.options`) need no change — they read as outlined shapes on black, which is the whole point of the border-not-fill rule.
  - **Consequence — the tower/pane splitter is visible at rest.** The `.splitter` sash was deliberately transparent, its own comment stating that *"the tower/pane background change marks the boundary"* — a premise one black surface deletes. It now rests at **1px of `border`** and still goes `accent` on hover/drag. It is the tower's **only** divider: `.tower-filter`'s `border-bottom` was dropped in the same pass, so the filter bar and the cards below it sit on one uninterrupted ground. The sash *is* the sidebar divider; there is no separate rule. **This also surfaced a latent bug:** the sash had no `box-sizing`, so `width: 5px` was the *content* box — it measured 9px and painted a **5px** bar, which its own comment ("visible line is the content-box, width minus padding") had always claimed was 1px. Invisible while it rested transparent, fat the moment it rested on a line. `box-sizing: border-box` makes the comment true.
  - **Consequence — the card wash doubled, `8%` → `16%`** (later a setting — see the card controls below). The one `color-mix(in srgb, var(--dir-color) N%, var(--bg-subtle))` in `App.svelte`. At 8% over Primer's `#161b22` the ground did most of the work; over black, 8% of the colour *is* the entire card (blue landed at `#040b14`), so cards stopped reading as surfaces. 16% puts blue at `#091628` — still unmistakably a dark card, now unmistakably blue. One number for both themes; light's cards get correspondingly more colour, which is the accepted cost of not forking the value per palette. The 2px edge tab stays full-strength `--dir-color`.
  - **Scrollbars lost their arrow buttons (2026-09-11).** The palette used to reach every scroller through one inherited `scrollbar-color` on `.shell`; it now paints the `::-webkit-scrollbar-*` pseudo-elements instead, with `::-webkit-scrollbar-button { display: none }`. Two facts, **both measured in this Electron (43.1.0)** rather than assumed, force that shape: (a) `scrollbar-width: thin` does **not** drop Chromium's Fluent arrows — it only narrows the bar 15px→10px; (b) Chromium **ignores every `::-webkit-scrollbar-*` rule on an element that also sets `scrollbar-color`**, so the two cannot coexist and the standard property had to go outright. The pseudo-elements don't inherit, so a single `:global(.shell ::-webkit-scrollbar-*)` descendant rule stands in for the old one-liner — `html`/`body`/`#app` are `overflow: hidden`, so **every** scroller in the app is inside `.shell`. **The bar is also narrower and squarer than Chromium's (2026-09-11):** a **10px** track carrying a **6px** thumb with 2px of clear space either side, at the **cards' own 2px radius** — the chrome is a stack of boxes cornered at 2px or less, and a 15px pill read as a piece of furniture beside them. Built as `background-clip: padding-box` behind a `2px solid transparent` border, the same inset recipe the first arrow-less version used at 15px/9px/pill (a flush thumb with no margin reads visibly fatter — measured, it was 1px *wider* than Chromium's and lost the clear space that made it look slim). **The bar became a hairline (2026-09-11):** an **8px** track carrying a **1px** thumb, the weight of the card's title rule and archive divider, so it reads as one more hairline in a chrome made of hairlines instead of a piece of furniture. Same inset recipe, new numbers — `8 − 4 − 3 = 1`, the odd half-pixel spent as an **asymmetric** border (right and bottom at 3px) because a fractional `border-width` snaps to the device pixel grid and lands on 0 or 2. It is a hairline to *look* at, not to hit: Chromium hit-tests the thumb's whole border box, so all 8px stay grabbable. **One bar everywhere:** the tower briefly had a narrower exception of its own and it was dropped — two scrollbar looks in one window is one more than this app needs. Thumb colour is still `border` on a transparent track. xterm draws its own scrollbar from the `scrollbarSlider*` theme options and never had arrows.
  - **Known flattening, accepted:** the Preview's *inline* `code` chip is a `bgSubtle` fill with no border, so on dark it reads as mono text rather than a chip (fenced `pre` blocks keep their border and are unaffected). The trailer canvas (`BG` in `trailer/src/lib.tsx`) still sits at `#0d1117`.
- **Muted ink is the theme's own ink at half strength (2026-09-11).** `fgMuted` stops being a grey picked per palette — light's Primer `#656d76` and dark's re-derived `#848484` — and becomes **`rgba(0, 0, 0, 0.5)`** in light, **`rgba(255, 255, 255, 0.5)`** in dark. The point is that it **composites** rather than being mixed once: a colour that resolves against whatever ground it lands on is what the *Dark selected card* setting below needs, since a card borrowing the dark tokens has to give its muted text the right value over ITS ground, not over the app's. It is close to a no-op everywhere else — measured, `#808080` on white against Primer's `#656d76`, and `#808080` against `#848484` on the black canvas. **Two uses are fills, not ink, and both were checked:** the Settings switch knob (which reads the same either way) and the exited status dot, which carries its own `opacity: 0.5` on top — the doubled fade lands within a tone or two of where it already was, in both themes, so the extra opacity stays. **The xterm scrollbar's hover tone keeps the old opaque hex** (`#656d76` / `#848484`): it is a canvas colour, not a CSS value, and cannot composite.
- **The cards line up with the filter bar, at every card count (2026-09-11).** The tower body used to be padded `0 8px 0 4px`, so the cards started 4px in while the search box above them started at 8px, and the right edge moved by the width of the scrollbar the moment the list outgrew the fold. It is now **`padding: 0 0 0 8px` plus `scrollbar-gutter: stable`**: left is the filter bar's own 8px, right is the gutter reserved at the scrollbar's full track width whether the tower scrolls or not. **The two numbers are one number** — the gutter *is* the 8px track, which is why the bar above was taken to 8px — so a card box is the search box's box, and adding the session that makes the tower scroll no longer resizes every card.
- **The selected card, and three controls for the cards (2026-09-11).** The card that owns the focused session paints its wash at full-ish strength while every other card keeps the 16% constant — one card lit at a time, so *which repo am I in* reads from across the room without inventing a second highlight idiom (the focused **row** keeps its own `bg` fill — plus a 1px border outline until 2026-09-12, when it came off as a second box inside the card's own edge; the card is the coarser answer). Membership is the same live-plus-archived sweep `rollupDot` already does, so a focused archived row lights its card too. Both numbers that were guesses became **Settings controls under Appearance**, because the right answer depends on the monitor and on how many cards are on it:
  - **Selected card — `10% / 50% / 100%`** (`ui.cardWash`, default `1` since 2026-09-12, `0.5` as shipped), the mix percentage for `.card.active`. At 100% the card is the raw `DOT_COLORS` hex and the muted text on it gets thin; that is the point of offering 10 and 50.
  - **Unselected cards — the same steps plus `None`** (`ui.cardWashRest`, default `None` since 2026-09-12, `0.1` as shipped), i.e. `None / 10% / 50% / 100%`. `None` is `background: none`, **not** a 0% mix — on light those differ, one being transparent and the other `bgSubtle`'s plate — and it leaves an unselected card as whatever its edge and its rows make it. This **replaced the 16% constant** recorded in the bullet above: the wash that was tuned once for the black canvas is the one thing the number of cards on screen changes most, so it became the second knob off the same list rather than a third hard-coded value. Ten is the nearest offered step to the 16% it replaces, so it shipped a touch quieter than the constant before it; the default is `None` now.
  - **Card edge — `Tab / Outline / None`** (`ui.cardEdge`, default `none` since 2026-09-12, `tab` as shipped), the card's colour **edge and nothing else**. `tab` is the original 2px tab welded to the left edge, `outline` a 1px `--dir-color` line around the whole card, `none` neither. It applies to every card, selected included — the selected one is already marked by its stronger wash, and a second edge idiom would say the same thing twice. **Deliberately orthogonal to the washes:** `outline` first also forced the background off, which made it a *look* rather than a control; the two were split so that outline-only is `outline` + a 10% rest wash and fill-only is `none`, and neither setting can surprise you by moving the other.
  - **Dark selected card — a switch, light mode only** (`ui.cardDark`, default **on** since 2026-09-12, off as shipped). The selected card borrows the **dark palette** for every chrome token its contents read — the grounds and inks (`bg`, `bgSubtle`, `fg`, `fgMuted`, `border`), the `accent` (spawn hover, drop hints, the rename field), `danger`/`success` (the close hover, the coloured title glyph) and the four status-dot fills. **The list is exhaustive on purpose:** leave one token out and it is the single tone in the card still speaking light, which is exactly what you see first. Nothing else moves: the wash recipe above is untouched, it simply mixes over a dark ground now, and every rule below still says `var(--fg)`. That is the other half of the two wash controls — they say how much colour a card carries, this says what it is carried over, which is what decides whether a 50–100% wash of a saturated colour is readable at all. In light mode the selected card becomes a dark plate with white text inside a light app, identical to what that card is in dark mode. **In dark mode it is a no-op by construction** (the borrowed palette *is* the live one), so the `data-card-dark` attribute is only set while the effective theme is light — and the switch still shows in dark rather than appearing and disappearing as a `system` theme follows the OS. Implementation note worth keeping: redeclaring `--bg-subtle` on `.card.active` is enough to move the background the *same* selector paints, because a custom property resolves to the winning value on the element where it is **used**. The mirror of that fact cost a round: **an inherited value is computed where it is declared**, so `color`, coming from `.shell`, had already resolved against the light `--fg` before it reached the card and no token override on the card could touch it — the card title and the branch rows declare their own colour and went white, while the session names, which only inherit, stayed dark. `.card` now re-declares `color: var(--fg)`: a no-op in every other mode, and what makes the card the colour boundary the whole feature assumes it is.
  - **A rule under the card title (2026-09-11).** An open card draws a 1px line under its name, spanning exactly what the archive divider spans at the other end, so the card reads as a bracketed list rather than a stack of loose lines. It carries `--dir-color` at rest and `--fg` on the selected card. The wash difference between selected and not can be slight — at `Unselected cards: None` plus a 10% selected wash it is nearly nothing — so the header line answers *which card am I in* when the fill can't. A folded card drops it: nothing is under the title to divide.
  - All four persist (optional/additive, no version bump) and are **validated on restore**, not trusted — the washes feed `color-mix`, so an arbitrary number out of a hand-edited state file would reach CSS as-is.
  - **Ethos note:** this takes the Settings panel to six pickers and four toggles. It stays inside the existing line — appearance only, no gallery, no per-colour customisation — but it is the closest the panel has come to it, and the next card knob should replace one of these rather than join them.
- **The defaults became the configuration the app is actually used in (2026-09-12).** Every Appearance default was re-baselined to Carlos's own running setup, read out of his state file rather than guessed: **Dark** (was System), **Status RGB on** (was off), **Color title glyph on** (was off), **Status detection: Screen** (was Hooks + poll), and for the cards **Selected `100%` / Unselected `None` / Edge `None` / Dark selected card on** (was `50%` / `10%` / `Tab` / off). The three fonts are unchanged (Cascadia Mono, Inter, Inter) because they already were the defaults. **No mechanism moved:** every switch still does exactly what its own entry says, and each is one click from the value it shipped with. It reaches a **fresh profile only** — a default is what an *absent* field reads as, so an existing state file still restores whatever it holds, and the defaults live in exactly two places that must agree (`ui`'s initial object and `restoreState`'s fallbacks, both in `sessions.svelte.ts`). Two are worth naming out loud. **Status RGB on** makes the literal red/amber/green what a first run shows: the tower is a race graphic, the pure hues are why it reads from across the room, and the Primer tones become the option rather than the baseline. **Screen as the default status technique** supersedes the *"ships off by default, behind a named switch"* clause in the screen-scan entry — the buffer scan is now what a Claude row uses unless you switch it off. That is Carlos's call, made after living with both; the switch stays, and the ethos argument for keeping it is unchanged.
- The mode themes the **Agent Race Control chrome only**: the Svelte tower UI, plus the xterm foreground/background + 16 ANSI colors, all set from the chosen GitHub palette. No per-color customization.
- **Typography — three user-selectable font families (decided 2026-07-16, superseding the earlier "chrome font is fixed" note):** all three live in the Settings menu as radio groups, **font-family only** (size stays the Ctrl+=/−/0 zoom). (1) **Terminal** (mono, `ui.font`) — the xterm panes *and* the preview's code blocks; the `FONTS` list. (2) **Interface** (sans, `ui.uiFont`) — the app chrome, applied as `--ui-font` on `.shell`. (3) **Preview** (sans, `ui.previewFont`) — the conversation-preview *prose only*; its code blocks follow the Terminal font. The sans list `UI_FONTS` is shared by Interface + Preview: **Inter** (default, bundled) · **Segoe UI** and **Arial** (Windows-native, zero-bundle — Arial is Windows' Helvetica substitute; real Helvetica isn't free to ship) · **Roboto** and **IBM Plex Sans** (bundled). Every bundled stack keeps `system-ui` as the fallback for non-latin titles/paths. Bundled faces (mono and sans) are **woff2-only, registered by hand in `main.ts`** — @fontsource's CSS also references a paired `.woff` that Chromium never loads, ~248 KB of dead installer weight avoided. All three ids persist in the state JSON (additive/optional). Rationale for deviating from a pure system stack: the app borrows GitHub's *colors*, not its typography — a design choice, not a fidelity break. **Ethos note:** three pickers plus three display toggles (Status RGB, Status dot, Color title glyph) is a genuine settings surface for a "minimal" app — all user-directed, kept to font-family/one-toggle, no theme gallery. See the resolved terminal-font item below for the box-drawing/ligature findings.
- `System` follows the OS via Electron's `nativeTheme` (`shouldUseDarkColors` / `updated` event) and flips live when Windows changes.
- Persist the chosen mode in the state JSON.

### Claude Code stays pure — Agent Race Control never steers its theme
- Agent Race Control does **not** hint, force, or sync Claude Code's internal theme. No `COLORFGBG`, no config injection, no theme flags. Claude Code renders exactly however it would in Windows Terminal.
- This is a direct consequence of the full-fidelity ethos: Agent Race Control sets a genuine terminal palette (the GitHub colors above) and stops there. If Claude Code auto-detects the real terminal background and adjusts, that's *Claude* reading the true environment — which is correct and pure. Agent Race Control's appearance toggle and Claude Code's own theme are independent by design, and that's fine even if they don't match.

## Stack (decided — don't re-litigate unless you hit a real blocker)

- **Electron + TypeScript.**
- **Terminal UI:** `@xterm/xterm` (note the `@xterm` scope — the bare `xterm` package is legacy) plus `@xterm/addon-fit` for resize and `@xterm/addon-clipboard` for **OSC 52** — Claude Code copies to the system clipboard via OSC 52 (e.g. `/btw`'s `c` key), and xterm.js only honors it with this addon. (Verify addon compat with xterm 6 in Phase 2.)
- **OSC 8 hyperlinks (fixed 2026-07-18):** clicking a link Claude Code prints (e.g. a login URL) approved the browser's `confirm()` but then silently did nothing. Root cause: xterm's default link activation opens a *blank* popup first (`window.open()` with no URL, a popup-blocker dodge) and only sets `.location.href` on it afterward — but our `setWindowOpenHandler` (main/index.ts) sees that blank URL, fails the http(s) check, and denies it, so the popup is `null` and the real URL is never navigated to. Fix: a custom `linkHandler.activate` on the `Terminal` (Terminal.svelte) that keeps the same confirm-before-opening UX but calls `window.open(uri, '_blank')` with the real URL directly, so it flows through the existing http(s)-only guard correctly. Same guard, same escape hatch as the preview's links — just no longer routed through the broken two-step popup.
- **PTY backend:** `node-pty` (a full pseudo-terminal is required because Claude Code is a full-screen TUI — plain `child_process` won't do).
- **Tower / renderer UI:** **Svelte** (with TypeScript). Chosen deliberately: Svelte compiles to small vanilla JS with ~no runtime, so it keeps the dependency/footprint story consistent with the minimal ethos while giving us real reactivity for the tower and appearance state. No React.
- **Bundler:** Svelte needs a compile step, so we add one — **Vite**, via **`electron-vite`** (main + preload + renderer configs, HMR in dev). This is the one new moving part the Svelte decision brings; keep the config stock and minimal.
- **Scaffold (decided):** hand-rolled, with the official electron-vite svelte-ts template open as a *reference* — not template-and-trim. Every file in commit 1 exists because we wrote it. (The template's `@electron-toolkit/preload` pattern exposes a general `electronAPI` — conflicts with our minimal explicit contextBridge, so it'd be ripped out anyway.) Escape hatch: if the hand-rolled config fights us in Phase 1, fall back to template-and-trim and say so.
- **Icons:** Google **Material Symbols** (outlined set), self-hosted via the `material-symbols` npm package — bundled locally, never from a CDN (CSP + offline). **The session-type icons are the exception (2026-08-19, revised 2026-09-09):** there are three of them and each is **inlined as geometry**, never pulled in as an icon package — a whole webfont for one glyph, three times over, is not a trade the minimal rule allows. Two of the three are **product marks**, which is the fact that drives everything else here: `claude` is the **Claude Code mark**, monochrome variant (thesvg.org, from `glincker/thesvg`'s `icons/claude-code/mono.svg`), and `openai` is the **OpenAI 2025 symbol** (Wikimedia Commons, `OpenAI_logo_2025_(symbol).svg`) naming the codex rows. A product mark names its row type the way a logo does and may not be redrawn to a house style, so the **shell glyph is the piece that gives**: Phosphor `terminal-window` (MIT, `@phosphor-icons/core` 2.1.1) sits at the family's own **regular** weight. It was bold only to stand level with the outlined Lucide `bot` that used to be the Claude row — that pairing, and the stroke-fraction measurement that balanced it (`2.25/24 = 24/256 = 0.09375`), **are gone with the bot**; all three entries are filled glyphs now and none is weight-matched. What each entry still carries is its own `box` (24 for the Claude mark, a padded ~20 for OpenAI, 256 for Phosphor) and a `stroke` **width** (0 = filled, which all three are today). The remaining balancing act is **size**, expressed as the fraction of the viewBox a glyph fills: the Claude mark occupies 62% of its box's height and the terminal 81% of its width, while the OpenAI source crops edge to edge and dominated the icon column until it was padded to ~85% by **growing the viewBox around the glyph's centre** — the vendor path stays byte-for-byte. `evenodd` is per-glyph too: the Claude mark's notches are subpaths punched out of the body and fill solid under the default nonzero rule. Shapes are held as a `paths` array and rendered as real elements — deliberately not an `{@html}` blob, which would put SVG children through HTML parsing. Rendered by an `icon` **snippet** in `App.svelte` (class `.svg-icon`), not a component: an `<svg>` from a child component would not match this file's scoped `.tab .svg-icon`-style rules, and the alternative is sizing ten call sites by hand. The svg is `1em` square with `flex: none`, so the same per-container `font-size` rules drive both icon systems; each of those rules names `.svg-icon` alongside `.material-symbols-outlined`. Note neither set has a `-plus` variant, so the **new-session** buttons carry the same glyph as the row icon — the add/plain distinction the Material `_add` variants gave us is deliberately given up. Version pin worth knowing: `terminal_add`/`dashboard_2_add` (the Material variants, now unused) only exist from **material-symbols 0.46.0**, and the package's `index.d.ts` name list is **not** authoritative for what the font can render — deprecated glyphs (`expand_more`, in use as the filter caret) ship in the woff2 while being absent from the list, so check the font's GSUB ligature table, not the metadata.
- **State:** a small JSON file in Electron's `userData` dir. No localStorage, no DB.
- **Tooling (added post-0.1.0, 2026-07-13):** **Prettier** (+ svelte plugin) locking in the existing style — no semis, single quotes, 100 cols, no trailing commas; markdown and the lockfile ignored. **Vitest** (pinned, peer-checked against the pinned Vite 7) for **unit tests over pure logic only**: the transcript reducer `parseLine` (the format is expected to drift — the tests document the shapes we handle, and a test breaking on a Claude update is the drift alarm), the empirically-verified `transcriptPath` encoding, `cleanTitle`, the `nudgeStatusFromKey` byte semantics, and the `applyPreviewItems` reset protocol. Deliberately no component tests and no E2E — the app's core surface is a real ConPTY terminal, exactly what E2E frameworks are worst at; visual testing stays the verification method for UI. **Mutation testing (added 2026-07-20):** **StrykerJS** (`@stryker-mutator/core` + `@stryker-mutator/vitest-runner`, devDeps, `npm run test:mutation`) drives the existing Vitest suite to measure test *quality* — whether the tests kill injected bugs, not just execute lines. Scoped to exactly the three tested modules (`transcript.ts`, `git.ts`, `sessions.svelte.ts`); mutating anything else is 100%-survived noise. Empirically settled the two risks before adopting: the vitest-runner drives **Vitest 4** fine (peer `vitest >=2`, no cap) and Stryker **instruments the `.svelte.ts` runes module cleanly** — 0 instrument/compile errors, the svelte compiler accepts the instrumented output. **Read the `covered` mutation score, not `total`:** these files intentionally interleave unit-tested pure logic with app-verified I/O (file watchers, git spawn, IPC/persistence), so the several-hundred no-coverage mutants in that plumbing drag `total` down by design. ### Technical specifics that are easy to get wrong — get these right
- `node-pty` is a **native module** — but since v1.1 it's **Node-API** and ships **prebuilt Windows binaries** (`prebuilds/win32-x64/`: `pty.node`, `conpty.node`, `winpty.dll`, `winpty-agent.exe`). Node-API is ABI-stable across Node *and* Electron, so **no `@electron/rebuild` step is needed** — the old "rebuild for Electron's ABI" advice is obsolete for this package. (Verified the hard way: the 1.1.0 npm tarball can't even be gyp-rebuilt on Windows — it ships without winpty's `GetCommitHash.bat`. Prebuilds are the only supported path from the tarball.) Caveat: the loader prefers `build/Release` over `prebuilds/`, so never leave a stale/partial `build/` dir inside `node_modules/node-pty`. On Windows it uses ConPTY under the hood, which renders Claude Code's TUI correctly. (The tarball carries **every** platform's prebuild directory on every host, and the darwin ones ship `spawn-helper` without its execute bit — see the macOS section for the chmod that has to happen before packaging.)
- **Security model:** `contextIsolation: true`, `nodeIntegration: false`. Run `node-pty` in the **main process**; expose a minimal, explicit API to the renderer via a **preload `contextBridge`** (e.g. `spawn`, `write`, `onData`, `resize`, `kill`). Shuttle bytes over IPC — keystrokes renderer→main, output main→renderer, plus resize events.
- **Shell (decided, non-negotiable):** spawn **Git Bash** (`bash.exe`) via node-pty and run `claude` inside it — Git Bash is Claude Code's recommended shell on Windows. Every terminal Agent Race Control opens is a Git Bash session; we do not offer PowerShell/cmd/WSL as alternatives. **Amended 2026-09-12:** non-negotiable **on Windows**. Off Windows there is no Git Bash to spawn, and `shell.ts` dispatches to the user's `$SHELL` — see *macOS: Windows first, macOS in progress*.
- **Bash resolution (decided):** adopt VS Code's battle-tested algorithm (`terminalProfiles.ts`) essentially verbatim. **Never PATH-resolve `bash.exe`** — on Windows that can hit the WSL stub (`WindowsApps\bash.exe`) or legacy WSL launcher (`System32\bash.exe`). Instead:
  1. PATH-resolve **`git.exe`** (no WSL doppelgänger, and it's the Git the user actually uses) and walk up from `<root>\cmd\git.exe` to the install root.
  2. Add standard install roots from env vars (`ProgramW6432`, `ProgramFiles`, `ProgramFiles(X86)`, `%LOCALAPPDATA%\Programs`) and the scoop locations (`scoop\apps\git\current`, `scoop\apps\git-with-openssh\current`).
  3. For each root, try `bin\bash.exe` first (the wrapper that sets up the MSYS env — never `git-bash.exe`, which spawns its own mintty window), then `usr\bin\bash.exe`. **First path that exists wins.**
  4. No registry lookup — keeps deps at zero and matches VS Code.
  5. If nothing is found, fail loudly with a clear "Git Bash not found" error. Optional `bashPath` override key in the state JSON as an escape hatch (no UI for it).
- **Spawn spec (decided):** always a **login interactive** shell — sources the user's profile, so PATH (e.g. `~/.local/bin` where `claude` lives) resolves byte-for-byte as in a regular Git Bash terminal; same args VS Code uses for its Git Bash profile.
  - **Shell session:** `bash.exe --login -i`
  - **Claude session:** `bash.exe --login -i -c 'exec claude --session-id <uuid> --settings <Agent Race Control-hooks-file>'` (resume: `--resume <uuid>` instead of `--session-id`). The `--login` still sources the profile before `-c` runs, so `claude` resolves from the user's real PATH; `exec` makes bash *become* claude, so the PTY's lifetime **is** the claude process's lifetime — `running`/`exited` fall straight out of the PTY with no child-process tracking. Deliberate consequence: when claude exits, the session ends rather than dropping to a prompt — the tower models Claude sessions, not shells; if I want a shell, I open a shell session.
  - The extra flags are the *only* deviation from a bare `claude` launch, and all are user-typeable CLI arguments, not config mutation: `--session-id` pins the id Agent Race Control already needs for resume, `--settings` adds the observability-only status hooks (see open items), and — only when the user asks a repo card for a fresh worktree — `--worktree <name>` (see *Worktree workflow*). Claude's behavior is otherwise byte-identical.
- **Session files live on disk** at `%USERPROFILE%\.claude\projects\<encoded-project-path>\<session-id>.jsonl` (the encoded dir name dashes **every non-alphanumeric character** of the absolute path — dots, spaces, underscores too; verified empirically 2026-07-13, and `[\\/:]`-only encoding silently broke both preview and `--resume` for dotted paths. The base dir honors a relocated `CLAUDE_CONFIG_DIR`). Useful for names/status, but note the key advantage below.
- **Status — keep it simple.** Because Agent Race Control *spawns* the sessions, it owns each PTY, so `running` / `exited` are known directly from the process. For the `waiting-for-input` signal, wire a lightweight Claude Code **hook** (Notification / Stop) that writes a small marker Agent Race Control watches. Target status set: `running`, `waiting`, `idle`, `exited` for Claude sessions; shell sessions are just `running` / `exited`. Don't over-model it.
- **Name & color (naming model revised 2026-07-12):** a Claude session's display name *is* the conversation's live name, read from the terminal title. Renaming in the tower types `/rename <new name>` into the session (documented inline-argument form), and a rename made inside Claude Code flows back through the title — **two-way by construction, one source of truth (Claude's)**. One wrinkle (observed): Claude doesn't re-emit the terminal title immediately on `/rename`, so the tower optimistically sets the *title itself* to the new name, overwritten by the next real title emission — `name` never holds Claude labels (it's the shell-only label field; the earlier name-override scheme got wiped by the session's first title event). A shell rename is a local label that shadows the title (Git Bash titles the path). The cwd basename is never shown as a session name: the old spawn default (`name` = basename) is gone, and pre-v2 state files are discarded wholesale on load (see the pre-1.0 no-compat policy under *Stack → State*), so a deliberate shell name is never second-guessed. **Blessed injections (`/color`, `/rename`) are typed only at the idle prompt** (tightened in review 2026-07-13, one shared `injectCommand` guard): while `waiting` the trailing Enter would answer the open permission/question dialog, and while `running` the input box may hold a draft; a rename that can't inject changes nothing (a visible no-op beats a silent revert), and blur-committing an unchanged rename injects nothing. Color belongs to the **directory group** (team stripe; right-click the header picks from Claude's 8-color `/color` vocabulary — red/blue/green/yellow/purple/orange/pink/cyan); the session context menu's **Apply folder color** types `/color <name>` into that session so Claude's agent view tints to match (useful after resume — Claude's color is runtime-only and resets). Known asymmetry (verified empirically; upstream: claude-code#41466/#49293): `/color` set *inside* the TUI can't be read back (lands in no file, no escape sequence), so sync is one-way app→session. Persist shell names and directory colors in the state JSON. **Row text = the terminal title verbatim (2026-08-19):** the tower strips only the MSYS `MINGW64:` prefix (the terminal describing itself, never part of a name) and shows everything else as emitted — including Claude Code's spinner churn, which now animates in the row. Same string the Session tab's *Terminal title* shows, which is the point: two places claiming to show the title and disagreeing is the class of thing the inspector exists to catch. The name-shaped read (spinner off too) survives as `cleanTitle` for the one place a title is *proposed* as a name — the rename prefill, which types it into a live session, where a captured spinner frame would become the actual name. No session-type branch: a shell never emits the spinner, Claude never emits `MINGW64:`.
- **Persistence across restarts:** the PTY is a child of Agent Race Control, so closing Agent Race Control ends the process — but the Claude Code *session* persists on disk. On relaunch, reopen a session with `claude --resume <session-id>`. This gives tmux-like continuity **without tmux** (I'm deliberately off WSL/tmux).

## Open items — decide along the way (flagged, not decided)

These were flagged during planning; resolve each when its build phase arrives rather than up front:

- ~~**Scoping the `waiting` hook**~~ **RESOLVED (Phase 5):** the jobs dir turned out to hold *background agents only* — foreground sessions never appear there. Instead: each Agent Race Control Claude session is spawned with `--settings <Agent Race Control-hooks-file>` (empirically verified: hooks fire from `--settings`), whose hooks (`UserPromptSubmit`/`PostToolUse` → running, `Notification` → waiting, `Stop` → idle) POST their JSON to a token-guarded localhost server in Agent Race Control's main process. Observability-only (always answered 200 `{}`), per-session, zero global config, zero files, zero polling.
- ~~**PTY → session-id mapping**~~ **RESOLVED (Phase 5, early):** `claude --session-id <uuid>` exists — Agent Race Control generates the UUID at spawn, so the mapping is deterministic. Verified: the id appears in hook payloads and names the transcript file. `--resume <that-uuid>` is Phase 6 plumbing only.
- **Hooks are blind to user interrupts (found + fixed 2026-07-12):** documented behavior — `Stop` fires only on normally-completed turns, and *no* hook fires when a permission/question dialog is dismissed (Esc) or a running turn is interrupted, so dots stuck amber/red after a cancel. Fix: the renderer *observes* the keystrokes it already forwards to the PTY (bytes pass through untouched — observation, not steering, same spirit as the title): **Ctrl+C** (`0x03`) while `running`/`waiting` → `idle` (an unambiguous interrupt/cancel); **a lone Esc** (`0x1b` alone; arrows etc. arrive as longer chunks) → `idle` **only while `waiting`** (dismissing a dialog); Enter while `waiting` → `running` (approve and deny-with-feedback both resume the turn). **Esc while `running` deliberately does *nothing* (issue #6, 2026-07-17):** it originally mapped to `idle` (interrupt), but Esc while running is ambiguous — it also just closes the slash-command menu / `/btw` overlay without stopping the turn, so it was wrongly greening a busy Claude. Same lone `0x1b` byte, indistinguishable, and no hook fires either way — so we drop the running-interrupt nudge (Ctrl+C still interrupts-to-idle instantly). Accepted trade-off: a genuine Esc-interrupt of a running turn no longer greens until your next action — the *safe* wrong direction (false-red "busy" beats false-green "your turn" while Claude is still working). Optimistic nudge only — the next hook event stays authoritative. ~~Parked: `PermissionRequest` and `Notification` payload types~~ **verified empirically same day** (probe: throwaway `claude --settings` session POSTing every event to a capture server) **and fixed:** (1) the false amber was real — exactly 60s after `Stop`, `Notification` fires with `notification_type: "idle_prompt"` ("Claude is waiting for your input"); the status server now **drops that type** (all other notification types still map to `waiting` — conservative default for unknown future types). Deliberately *not* mapped to `idle`: unverified whether the nag can also fire while a dialog sits open, and `Stop` already covers the green. (2) **`PermissionRequest` → `waiting` added:** it fires the instant a dialog appears — including `AskUserQuestion`, which surfaces as a `PermissionRequest` with that `tool_name` — whereas the `permission_prompt` Notification trails it by ~6s (it's the OS-notification pathway); amber is now immediate, and the late Notification lands on an already-amber dot. The probe also confirmed per-payload `session_id` routing — cross-session status leakage isn't possible. **Out-of-order `PostToolUse` fix (2026-07-15):** a second stuck-red cause, distinct from interrupts. The status hooks are non-blocking observability POSTs (the server answers `200 {}` without Claude waiting), so their HTTP requests race each other; when a turn ends right after a tool call, `PostToolUse` (→running) and `Stop` (→idle) fire near-simultaneously and can be delivered out of order, flipping a just-finished dot back to red. The *focused* session self-heals on the next keystroke/turn, but a session you've **switched away from** — or one that went red **while you were viewing another** — has no keystroke nudge, so the stray red sticks. Fix: the hook→status mapping moved out of `status.ts` into a **turn-aware state machine in the renderer** (`applyStatus`, now co-located with the keystroke nudge — one owner). Main forwards the *raw hook event*; the renderer treats `PostToolUse` as "still in a turn" — it may hold `running`/`waiting` red but **never resurrects `idle`**, and only `UserPromptSubmit` (a genuine new turn) leaves `idle`. No heuristics, still pure observation. Covered by an `applyStatus` unit test.
- **Spinner-driven idle — the interrupt watchdog (issue #6 follow-up, 2026-07-17):** an empirical probe (node-pty, four cases: normal completion / Esc-interrupt / `/btw`+Esc / Ctrl+C, watching hooks + title + transcript side by side) confirmed what the docs say — **no hook fires on any user interrupt or menu/dialog dismissal** (design: hooks are turn-lifecycle, not UI events). The one signal that survives is the **terminal-title spinner**: Claude animates the title (`✳✶✻✽` churn *and* braille `⠀-⣿` frames) while a turn runs and stops when it ends. It was the *only* channel that caught the Esc-interrupt (no hook, no transcript marker) AND correctly kept "busy" through `/btw`+Esc. So we watch it: `noteTitleForStatus` re-arms a decay timer on every spinner-bearing title of a **`running`** session; when frames stop for `SPINNER_IDLE_MS` (1200ms) the turn ended → `idle`. **Scoped to `running` only** — a `waiting` dialog (hook-owned; the spinner has already stopped) is left alone by the decay's `status === 'running'` guard, and normal completion (`Stop`) / Ctrl+C (keystroke) still idle *instantly*; the spinner is the ~1.2s-latency safety net for the hook-blind interrupt. The raw title flaps with a plain `claude` (the OS/ConPTY process title, no spinner) — ignored via `hasSpinner`; the decay (spinner-frames-only, re-armed) is robust to the flap. This **resolves the #6 patch's accepted trade-off** (a genuine Esc-interrupt now idles after the grace window instead of staying stuck red), and `cleanTitle` gained the braille range so names stay clean. Statusline was ruled out (rich metadata — context %, model, cost — but no busy/idle field, no state-change firing; parked for tower extras). The keystroke nudge stays for the *waiting* axis (Esc-dismiss→idle, Enter-answer→running) and instant Ctrl+C.
- **The watchdog had no margin — mid-turn false-green (found + fixed 2026-08-12):** reported symptom was a dot that "stays green most of the time when the thread is busy". Two node-pty probes (title changes, PTY byte arrivals and hook events timestamped side by side; scenarios: idle-at-prompt, long generation, permission dialog, long tool, **subagent**) plus a replay of the real state machine over the recordings all came back *clean* — 0% wrong green over 44s of busy time. What they did establish is the number that matters: **the title spinner ticks about once a second — 957-1055ms across four turns** — while `SPINNER_IDLE_MS` was **1200ms**. That is a watchdog set ~1.2x the period of the signal it watches: not a margin, a coin flip taken once per second, which is exactly why it is intermittent, why it favours busy sessions (more ticks = more draws), and why a quiet lab could not force it. Temporary instrumentation (every `setStatus` logged with its cause plus `sinceTitle`/`sinceHook`, written to `<userData>/status-debug.log` in dev builds) then caught it in a real session inside a minute: `UserPromptSubmit` → red, then **1215ms later `spinner-decay` with `late=8ms`** (the timer fired on schedule — jitter in the *signal*, not a stalled renderer) → green, then a `PostToolUse` 2s after that proving Claude was still working and being **discarded**. Ruled out along the way, each empirically: subagent runs (parent title keeps ticking through 24.6s of subagent work; subagent tool calls fire `PreToolUse`/`PostToolUse` on the *parent* session), renderer main-thread contention (`late=8ms`), non-spinner title flaps mid-turn (zero observed), and a turn-opening stall (post-prompt gaps are indistinguishable from mid-turn). **Two-part fix, because the trigger and the persistence were separate bugs:** (1) `SPINNER_IDLE_MS` 1200 → **4000ms**, ~4x the measured period, so ordinary jitter cannot reach it — the cost is bounded and on the safe side (an Esc-interrupt idles in up to 4s instead of 1.2s; `Stop` and Ctrl+C still idle instantly), the same false-red-beats-false-green asymmetry that removed the Esc nudge in #6; (2) **`idle` is no longer absorbing** — a `PostToolUse` now overturns an idle that came from the *decay* (a guess the tool call disproves) while still refusing to overturn one that came from `Stop`/Ctrl+C (an observed end-of-turn, where the out-of-order-POST race is the real hazard). This needed a `StatusCause` on `setStatus` — the cause is load-bearing, not just a log string — and recovery re-arms the decay so a session recovered by a trailing straggler can't sit red forever. Before, one bad guess owned the rest of the turn; now the correction arrives ~2s later on its own. The diagnostic logging was scaffolding and **was removed when the fix landed** — not kept anywhere, so if the bug ever returns it gets rebuilt: it was a dev-only `debug:status` IPC channel (main + preload) appending every `setStatus` to `<userData>/status-debug.log` with its cause and the `sinceTitle`/`sinceHook`/timer-`late` timings that told the candidates apart. **Still untested:** the `waiting`/amber path — `PermissionRequest` never fired in either probe (a `Bash` `echo` went `PreToolUse`→`PostToolUse` in 1.2s with no permission hook at all), so how amber is really triggered is an open question. Also parked: `PreToolUse` and `SubagentStop` are dense liveness signals the app receives and discards.
- **Status is QUERIED, not inferred — `claude agents --json` (settled 2026-08-13; supersedes the three bullets above).** The three entries above are the archaeology of one mistake: every channel we had reported **edges** (hooks fire on transitions, the title spinner stops, a keystroke suggests intent), so a missed edge left the dot wrong until the next one with no way to resync — and the spinner decay was the worst shape available, the only input that could manufacture the *unsafe* colour (green) without observing anything. Bumping it 1200→4000ms didn't change the shape, and a real 10-minute tool-sparse turn showed green the whole way. The fix is not another rule: **`claude agents --json` is an official, documented command that returns a JSON array of active sessions, each with a `status` field** — a *level*, queryable at any moment, so a wrong dot self-heals on the next tick instead of persisting to the end of the turn. Verified empirically on v2.1.229 before adopting: it lists **`kind: "interactive"`** sessions (the published docs claim interactive sessions don't appear until backgrounded — **false in practice**, and the one contract risk we accept here); the `sessionId` it reports is **exactly the uuid we pin with `--session-id`** (checked against our own state.json), making the join trivial; one call returns *every* session in **~275ms median** (71 polls); and status values observed live are **`busy`/`idle`** while the docs name `working`/`waiting`/`idle`/`done`/`failed`/`stopped` — so the mapping accepts **both vocabularies** and ignores anything unknown rather than guessing. `waiting` additionally carries `waitingFor` (`permission prompt`, `input needed`, `sandbox request`, `worker request`, `dialog open`) — which finally answers the amber question the old notes list as unverified; we map every `waiting` to one amber and deliberately do **not** surface the reason (out-of-scope). **Identity comes from the same poll**, which is why this replaces the hook server outright rather than sitting beside it: the entry carries `sessionId` (so `/clear` minting a new conversation id is just a changed field → the issue-#2 transcript follow) and `cwd` (so a `--worktree` spawn's real directory is adopted, replacing "cwd follows the hooks"). Matching is **pid-first, sessionId-second**: `claude.exe` is a *grandchild* of our PTY's bash (traced: claude → bash → bash → electron), so `pty.pid` is useless, but the claude pid is **stable across `/clear`** — so we learn it on the first sessionId match and follow it afterwards, with `startedAt` guarding against Windows pid reuse. **Deleted, not deprecated:** `src/main/status.ts` (the localhost hook server), the per-session `--settings` files, the keystroke nudges (`nudgeStatusFromKey`), the whole spinner watchdog (`noteTitleForStatus`, `SPINNER_IDLE_MS`, `StatusCause`/`idleCause`) and `hasSpinner`. **This retires a blessed deviation** — `--settings` is gone from the spawn line, so a spawned claude is now one flag (`--session-id`, plus `--resume`/`--worktree` when asked) closer to a bare terminal. **Cost accepted:** polling, which the doc otherwise avoids — mitigated by it being *one* subprocess per tick for *all* sessions (not per-session), gated to only run while a claude PTY is alive, and by resolving `claude`'s absolute path **once** through the Git Bash login shell (`cygpath -w "$(command -v claude)"`, the same never-PATH-resolve discipline as `bash.ts`: direct 273ms vs 403ms through a login shell per poll; the resolve is async so it never blocks the main process). Latency is one tick instead of a hook's instant edge — **measured end-to-end in the real app: dot goes red 1.5s after Enter, holds red for a full 90s turn with zero mid-turn greens, and greens only at the true end.** The deliberate trade of a little lag for a dot that is *correct*.
- **The poll's `busy` is not the dot's red — hooks own the turn, the poll is the floor (settled 2026-08-17, corrects the entry above).** Testing the poll-only build found the dot stuck red on sessions sitting at their prompt. Cause, measured directly: **`claude agents --json` reports `busy` for a session whose turn has ENDED but which still owns a background shell** — 90 consecutive samples over 205s, all `busy`, on a session that was idle at its prompt the whole time with one background shell alive (the probe polled its own parent session, so the log spans the turn boundary). Not a wiring bug — a **semantics mismatch**: the CLI's `busy` means "this session has something running", the tower's red means "the agent is driving". Persistently wrong, not intermittently: any session leaving a dev server or watcher running would sit red until you killed it. And the poll cannot be made to answer the right question — verified with a shell deliberately alive, the entry carries exactly `pid, cwd, kind, startedAt, sessionId, name, status` (`--all` adds `id`/`state`); **no shell count, no agent count, no qualifier on `busy`**. `subagentStatusLine` does expose a per-subagent `tasks` array, but it is a command run *inside* the session (so it needs settings injection anyway) and covers agents only, not shells. **Hence the hybrid, each side doing only what it is good at:** turn boundaries come from **hooks** (`UserPromptSubmit` → red; `Stop`/`StopFailure` → end of turn; `PermissionRequest`/`Notification` → amber) — precise, instant, and never the source of the old bug — while the **poll is a self-healing floor**: a tick reporting `idle` means nothing whatever is running, so it forces green; a tick reporting `busy`/`waiting` is **ignored**, because it cannot tell a turn from a shell. That keeps the one property polling was adopted for (a level resyncs, so a missed edge can't persist to the end of a turn) and takes turn semantics from the only source that has them. **Still much smaller than the original stack:** no spinner watchdog, no `StatusCause`/`idleCause`, and **no `PostToolUse` at all** — turn start and end are the only edges needed, which deletes the entire out-of-order-POST race the 2026-07-15 fix existed for. `StopFailure` is new and closes a gap the old code had: a turn killed by an API error fires no `Stop` and would otherwise stay red forever. **Costs, stated plainly:** `--settings` returns as a blessed deviation (the previous entry's claim that it was retired is withdrawn), and no hook fires on a user interrupt — so an interrupted turn in a session with a live shell would sit red, since the poll will never report `idle` there. That is closed with the **Ctrl+C keystroke nudge only**, the one piece of the old inference the notes call unambiguous; **Esc stays out** (its ambiguity with closing the `/btw` menu is exactly issue #6).
- **`delegating` — a fourth dot state for "subagents working, main agent idle" (settled 2026-08-17).** Shells are *not* busy from the user's point of view, but subagents are a real third thing: the session isn't asking for you and you aren't blocked, yet work is happening. It gets its own state — **the same amber as `waiting` but NOT pulsing** (the pulse stays exclusive to "it wants you", which is the only state that should catch your eye). **A busy main agent always wins:** while the main turn runs the dot is red regardless of how many subagents are going, so `delegating` only ever shows *after* the main turn ends with subagents still alive. Tracked by counting `SubagentStart`/`SubagentStop` per session: `Stop` resolves to `delegating` when the count is above zero and `idle` when it isn't, and the count reaching zero while delegating drops it to green. Drift is self-healing by construction — a missed `SubagentStop` is cleared by the poll's `idle` floor once everything really has finished, which is exactly what the floor is for. Roll-up order for a collapsed card becomes **waiting › running Claude › delegating › running shell › idle › exited**.
- **Agent view vs. the tower model** — left-arrow detach, `/attach`, and in-session `/resume` all mean a single PTY can *switch* which Claude conversation it displays, while the tower keeps the session-id pinned at spawn. ## Next phase (post-v1, agreed 2026-07-12): read-only conversation preview

A toggleable **markdown preview of the conversation** as a second view of the session. Read-only observation; the PTY byte stream stays untouched, so the fidelity ethos holds by construction.

- **Data source:** the transcript JSONL at `~/.claude/projects/<cwd-encoded>/<uuid>.jsonl` — the path is fully known because we pin `--session-id` at spawn (encoding: every non-alphanumeric dashed, see *Session files* above; `transcriptPath()` in `transcript.ts` is the single owner, and `pty.ts` reports the *effective* spawn cwd back so a dead-path fallback can't desync the tail from where Claude actually writes). **Main process tails the file** (fs.watch + incremental reads of appended lines), parses entries, pushes them to the renderer over IPC (same pattern as the status server, file-flavored) — **in bounded batches with yields between them** (added in review 2026-07-13): the first read of a watch is the whole file, and main's event loop also pumps every PTY, so it must never block for a full parse nor ship one unbounded IPC array. **fs.watch is backstopped by a ~1s stat poll while armed (added 2026-07-15):** Windows `fs.watch` on the directory *drops* change events — notably the final append of a turn, the byte range carrying the last assistant message — and the watch has no retry for a missed event, so flipping Terminal↔Preview mid-turn could strand the preview one turn behind (the ~50ms mount catch-up read races the final flush; if the following write's event is dropped, those bytes are never re-read). The poll — one stat/sec, only while a preview is open, watch still the low-latency path — schedules a read whenever the file has grown past the read offset, so the final state always lands within ~1s even when the event is lost. Renderer never touches fs; keep the preload bridge minimal. **Tail state is per-session and persistent (redesigned 2026-07-13):** the byte offset and line remainder live in one `TranscriptTail` per session id that outlives the preview — mounting a preview *arms* the watcher, unmounting only *disarms* it, so reopening reads just the delta; closing the session (`transcript:drop`) forgets it. The first batch of any from-zero read is sent `reset=true` (the renderer replaces its cache instead of appending), so truncations, re-created tails, and in-flight-delivery races can never duplicate items by construction.

- **We run the ConPTY Windows Terminal runs, and the PTY never disagrees with the grid (2026-09-12).** Reported as *the terminal doesn't scroll all the way up*, then pinned down: resize the window smaller and the agent's header came back **duplicated line by line**, a zoom in-and-out left five stacked copies of it, and the first lines of the session were gone.   - **`useConptyDll: true`** on the node-pty spawn (`pty.ts`). The built-in one is whatever that Windows build shipped with, and its reflow on resize is years behind. Parity with Windows Terminal means running the console host Windows Terminal runs. node-pty marks the flag experimental and falls back to the built-in ConPTY if the DLL won't load; the files reach a packaged build through the `asarUnpack: node_modules/node-pty/**` rule the `.node` prebuilds already need.

It is now subscribed before the spawn and guarded on `ptyId`, with a catch-up resize when the grid moved while the spawn was in flight. **xterm owns the grid; the PTY is never allowed to disagree with it.**

- **`/clear` re-points the tail — RESOLVED (issue #2, 2026-07-16):** Claude Code mints a **new session id + new transcript file** on `/clear` (confirmed empirically — a node-pty repro showed the hooks POST a fresh `session_id`/`transcript_path` after the clear). The app pinned `claudeSessionId` at spawn, so the preview tail — and, silently, the status dot *and* resume-on-restart — all stuck to the pre-clear file (preview froze on the old conversation, the reported symptom). **The enabler:** a `--settings` hooks file is read **once at process start**, so its hook URL is baked in for the process's life; every hook POST, before and after a clear, hits that same URL and carries the *current* `session_id`. **Fix:** each spawned session gets its **own** hook URL — a per-session `--settings` file with a session token in the path (`arc-hooks/<token>.json`, replacing the single shared `arc-hooks.json`; the dir is wiped on app start). The status server routes by that URL token (stable per session, independent of the conversation id) and forwards the payload's current `session_id`; the renderer, on seeing it diverge from the stored `claudeSessionId`, treats it as a clear — updates `claudeSessionId` (so resume-on-restart follows too), re-points the transcript tail to the new file, and resets the preview cache to the fresh conversation. One root cause, three symptoms fixed (preview + status + resume); the in-TUI `/resume` divergence (old flag 2, and the agent-view open item) is now followed for free. **Parked (2026-07-17):** the re-point lands on the *first post-clear prompt* (the first hook after a clear is `UserPromptSubmit`; nothing fires at the `/clear` keystroke itself), so the old conversation lingers in the preview until you prompt again. Clearing it *immediately* would need keystroke command-sniffing — fragile with Claude's slash autocomplete (you can pick `/clear` without typing "clear") and risks a false blank — so it's deferred against the observation-only ethos; the next-prompt re-point is the accepted behavior unless the lag bites in daily use.

- **One idle blink lost the dot for a whole turn — the floor gets two guards (found in the field + fixed 2026-08-19, refines the entry above).** Reported as "dot green but session busy", and diagnosed **from the Session tab's own Copy all output** — the first bug the inspector paid for. The paste made it unambiguous: last hook `SubagentStop` **34m 55s** ago (so the turn that opened ~35m earlier never reported `Stop`), our status last changed **14m 29s** ago, the CLI's own status last changed **14m 24s** ago and read `busy`, and the transcript had been appended **47 seconds** before the copy. Only two things can paint green — a `Stop` hook or the floor — and no hook had arrived, so the floor did it: the poll blinked `idle` for a single sample at ~15:25, we greened, the CLI went back to `busy` five seconds later, and the dot stayed green through 14 further minutes of real work. **Not lag — unrecoverable by construction:** red comes only from `UserPromptSubmit`, which that turn had already spent, and `busy` was ignored, so nothing could ever repaint it. **Ruled out first, empirically:** the session ran **2.1.235** against a contract verified on 2.1.229, and `status.ts` silently drops any POST missing `session_id`/`hook_event_name` — so a schema drift would look identical. Probed a real 2.1.235 claude against a copy of the app's own `--settings` file: `UserPromptSubmit` and `Stop` both POST with both fields. The hook contract is intact; the bug was ours. **Fix, two halves.** (1) **The floor is debounced while a turn is open:** `IDLE_TICKS_TO_END_TURN` = 3 consecutive `idle` samples (~3s at the 1s poll) before the floor may close a turn the hooks opened; any non-idle sample resets the streak, and with **no** turn open a single tick still greens instantly, so the common self-heal keeps its latency. While a turn is open and the dot is somehow green, a `busy` tick **restores red** — the ban on `busy` exists because it cannot separate an agent from a background shell, but a turn the hooks opened and never closed is exactly the context that separates them, and then the *green* is the claim that must be wrong. Amber and `delegating` are hook-owned and never overridden. **No regression in the case the ban was written for:** a missed `Stop` on a session holding a live shell already sat red under the old code (the floor never sees `idle` there), and still does — while Ctrl+C clearing `turnOpen` stops an interrupt's surviving shell from re-painting red. Both halves are unit-tested, including the exact field sequence (blink → still red; hold → green). `turnOpen` and the idle-tick count are surfaced in the Session tab, since hidden status state is what made this take a paste to see.

- **A row is a conversation, not a process — parking moved one out from under us (found in the field + fixed 2026-08-21, refines the entry above).** Reported as "why is this green", again diagnosed from the Session tab's Copy all: tower dot `idle`, last hook `UserPromptSubmit` **23s** ago, turn open **no**, poll `idle`, and the CLI's own status unchanged for **1h 24m** — a session that had been working the whole time. **Cause: the conversation had been parked.** Claude Code can move a session "to the background from this window" (its own words, read out of the binary), and when it does, `claude agents --json` reports **two** live entries: the interactive process we spawned, `idle` for as long as it stays parked, and a **`kind: background`** entry with its **own pid** and its own conversation id, `status: busy`/`state: working`, doing the actual work. The interactive session's `~/.claude/sessions/<pid>.json` gains a **`parkedJobId`** naming the job (cleared again on unpark), and the background job's transcript is a **copy of the interactive one up to the fork**, with every `sessionId` rewritten to the job's. **Hooks follow the conversation, matching followed the process** — that was the bug. The background process inherits our `--settings`, so its POSTs still route on our stable per-session URL token, but they carry **its** `session_id`; matching was **pid-first**, so every tick re-pinned the row to the idle husk. Two failures, both measured in the paste: (1) the **floor greened a working session** and no `busy` could restore red, because the busy entry belonged to a pid the row did not match; (2) hook and poll **fought over the conversation id** — each `switchClaudeSession` resets `turnOpen` and the idle streak, so one tick after every prompt the 3-tick guard was bypassed (`!turnOpen`) and the dot greened, while the preview tail was dropped **twice per hook** (a from-zero re-read of a 21MB transcript). The state proves the switch: nothing else can zero `idleTicks`, since the husk never reports non-idle. **Fix: `findEntry` matches CONVERSATION FIRST, pid second.** The id is what a row *is*; the pid is the fallback that carries it across a `/clear` (same process, new id, announced by nothing until the next hook) and is **adopted from whichever process is running the conversation** — so the Session tab and the preview follow the live background job too, both being keyed on `claudeSessionId` + `claudePid`. The Windows pid-reuse guard (`startedAt`) is unchanged. **Costs, stated plainly:** the unpark shape is **not verified** — if the interactive process resumes under an id we don't hold, the row matches nothing (no floor, dot holds its last hook state) until the next hook re-points it; the last hook a finishing job sends is its `Stop`, so the resting state is green, not a stuck red. **Parked, not built:** a third fallback on the immutable spawn id (`hookToken`) would shorten that window, but it is speculative until the unpark contract is actually measured. **The idle streak now starts at the prompt (settled 2026-08-24, same investigation).** Found alongside the above and fixed after it, separately: `idleTicks` was never reset when a turn *opened*, so the 3-tick guard only bit when the poll happened to see non-idle within the 3 ticks before the prompt. A session **idle at its prompt is the normal way to start a turn** — the counter is saturated by the time you press enter, so the first idle sample of the new turn, one that merely beat the CLI's own flip to `busy`, satisfied `idleTicks >= 3` and closed the turn on tick one. The 2026-08-19 debounce was therefore intact only by winning a ~1.3s race, and losing it cost the whole turn (green, `turnOpen` cleared, so `busy` could not restore red either). `UserPromptSubmit` zeroes the counter — one line in `applyHook`, and the guard now means what its name says: three consecutive idle samples **since this turn opened**.

- **The poll died silently when Claude Code updated itself (found in the field + fixed 2026-08-25).** Surfaced as a main-process warning, not a wrong dot: `UnhandledPromiseRejectionWarning: Error: spawn EBUSY` from `agents.ts`'s `execFile`. **Cause:** Claude Code auto-updates by replacing its own ~380MB `claude.exe` **in place** (the `claude.exe.old.<ts>` siblings are its receipts — two on the day this was found), and the poll spawns that exe **once a second**, so it lands in the swap window sooner or later. `child_process` reports that failure by **throwing synchronously**, so the callback's `error` branch — which exists precisely to make a bad tick a dropped tick — never runs. **The warning was the harmless half.** `schedule()` sat *after* the throwing call, so the throw skipped it: no timer was armed, `running` stayed `true` (so `startAgentPolling` early-returns and cannot restart it), and **the poll stopped for the life of the app**. Silently: hooks keep painting red and amber, so the tower looks alive, while the green floor — the whole self-heal — is gone until the app is restarted. **Fix, three parts, all in `agents.ts`:** the poll's `execFile` is wrapped in `try/catch` that reschedules; the chain gets a terminal `.catch(() => schedule())` so nothing whatsoever can kill the loop; and `schedule()` clears any pending timer before arming, making a double-call harmless (two live timers would fork the loop permanently, doubling again on every later fork). `resolveClaude` gets the same guard, plus one subtlety: a synchronous failure there must **not** be cached as "no claude on this machine" — the memoised promise is dropped when an attempt ends without learning a path, or every later call replays that resolved-null forever. **Verified** with a standalone repro of both loop shapes against a fake `execFile` that throws synchronously on the third call: old shape 2 ticks then dead (with exactly the reported warning), new shape ticking normally. **Flagged, not fixed:** `pty.ts`'s node-pty `spawn` has the same theoretical exposure, but it is an `ipcMain.handle` with an existing `{ error }` contract and its failure is *visible* (the session never appears) rather than silent, and `bash.exe` is not rewritten hourly the way `claude.exe` is.

## Session inspector tab (2026-08-19)

A **third tab in the pane strip — Terminal | Preview | Session** — on Claude sessions only: everything the app knows about the running session, as read-only labeled text. Purely an instrument panel. It brushes the minimal ethos (a diagnostics surface is exactly the kind of thing the out-of-scope list exists to stop), and it earns the exception on one argument: the status dot's correctness has been *unverifiable* by eye, which is what made the 2026-08-17/18 status rewrite take three attempts. This tab makes the disagreements observable — our computed dot next to the poll's raw `busy`, the hook-counted subagents next to the transcript-counted ones — and turns two claims we currently take on faith (that `SubagentStart`/`SubagentStop` fire at all, and that the amber `waiting` path is ever reached) into things you can watch. **Read-only text, one control** — see the copy button below; the tab reads, and the only thing it writes is the clipboard.

- **Three sources, no new channels.** (1) **What the app already holds** — the `Session` object plus, newly *retained* rather than discarded, the last raw agent-poll entry and the last hook event with its timestamp, and a `statusSince` stamp set in `setStatus`. Two fields, and they are the whole reason the tab is worth building. (2) **`~/.claude/sessions/<pid>.json`** — the file `claude agents --json` reads, which carries strictly more than the CLI prints: `version` (the Claude Code build driving *this* session), `statusUpdatedAt` (age in status), `nameSource` (`derived` vs a user `/rename`), `procStart` (a stronger pid-reuse guard than `startedAt`), `entrypoint`, and `bridgeSessionId` (`/remote-control` is live). (3) **the transcript JSONL we already tail for the preview**, folded to metadata instead of prose.
- **Facts folded from the transcript** (all verified empirically against real transcripts on v2.1.229, 2026-08-19): `ai-title` (the real conversation title the OSC title mirrors), `slug`, `mode` and `permission-mode` (`auto`/`default`/`plan`/`acceptEdits`/`bypassPermissions`, live per turn), per-assistant `model`/`effort`/`version`/`gitBranch`, and `message.usage` — `input + cache_read + cache_creation` is the **context size** (the same number Claude Code's own status line shows as `↓ 40.3k tokens`), plus output/thinking tokens and `service_tier`. From `system` entries: `turn_duration` (`durationMs`, `messageCount`) → turn count and last turn duration; `stop_hook_summary` (`hookInfos[].command`/`durationMs`, errors) → which hooks ran and how slow they were; `compact_boundary` (`compactMetadata.trigger`/`preTokens`/`postTokens`) → compaction count and window headroom; `away_summary` → Claude's own written summary of where the session got to; `bridge_status` → the `claude.ai/code` remote-control URL. Plus `last-prompt` and `queue-operation` — the queue is **modelled, not tallied**: measured, `enqueue` carries the content but `dequeue` and `remove` carry nothing, and Claude Code queues its own task notifications through the same mechanism, so a +1/−1 count read *3 prompts waiting* on an empty queue. Holding the contents in order and shifting on either removal nets correctly and lets the count exclude the notifications.
- **Agents and shells — counted as a LEVEL, which is the point.** Subagents are in-process API calls: invisible to the process tree, and absent from `claude agents --json` (measured — a real background shell shows up as a `bash.exe` child of `claude.exe`, alongside hook processes and the foreground tool's own shell, so a process-tree count can't distinguish them and is **not** used). The transcript can: a `Task` tool_use with no matching `tool_result` is a **synchronous subagent still running**, and an `async_launched` one (whose `tool_use` returns immediately with an `agentId`) closes when a `<task-notification>` carrying that id arrives. Background shells work the same way — `toolUseResult.backgroundTaskId` opens, the matching `<task-notification>` closes. Both are re-derivable from the file on every read. **Two corrections from probing the fold against a real 3.8MB transcript (2026-08-19), both of which had it reporting fiction:** (a) the completion notice arrives in *three* shapes depending on whether a turn was running when the task finished — a `user` message, a `queue-operation`, or an `attachment` — so the matcher runs against the whole line rather than user messages only; matching one shape left finished shells counted forever. (b) The counts are labeled **open**, not *running*: the transcript records a start and a completion, so anything whose completion was never written (the app outlived the run, the turn was interrupted) stays counted for the life of the conversation. Measured: 7 shells started, 3 still open, 1 of them genuinely alive. The Status section's poll line is the authority on whether the session is *actually* doing anything; these two say what it started and never closed. The transcript alone cannot close that gap, and reconciling the two channels here would repeat the mistake the status rewrite just undid. Subagent transcripts, if we ever want them, are at `~/.claude/projects/<enc>/<sessionId>/subagents/agent-<id>.jsonl`.
- **The literal status line is out of reach, and stays out.** `Billowing… (10m 29s · ↓ 40.3k tokens)` is rendered inside xterm. The only routes to it are scraping the terminal buffer (fragile, and it *is* the byte stream) or installing a `statusLine` command via `--settings` — which would **replace what the user sees in their own terminal**. Both fail the fidelity ethos; rejected. Every number in it is reconstructible from the transcript, so the tab shows its own honest equivalent rather than faking Claude's.
- **Cost:** the transcript fold is **incremental** — offset + remainder per path, same shape as `TranscriptTail`, so the multi-MB first read is paid once and each refresh parses only appended bytes. Refresh is a 2s interval that runs **only while the tab is visible**, and the `sessions/<pid>.json` read is one small file. No new polling when the tab is closed.
- **Flag carried in, same as the preview's:** `sessions/<pid>.json` and the transcript are internal, undocumented, and drift across Claude Code versions. Parse defensively, skip what isn't recognized, never throw, render "—" for anything missing. **The dot never reads any of it** — this tab is display-only, so a format drift degrades the inspector and cannot regress status.
- **Copy all — the one control, added 2026-08-19.** The original rule was *no controls at all*, on the reasoning that a button turns an instrument into a feature. It was overturned the same day for the reason the tab exists: the tab makes a wrong dot **visible**, but a diagnosis usually happens somewhere else — in a Claude session, in an issue — and re-typing thirty fields by hand is how you get a report with the one field that mattered missing or stale. A sticky **Copy all** in the pane header writes the whole panel as plain text. It still reads rather than acts: the only thing it writes is the clipboard, and it adds no source, no channel and no field that isn't already on screen. The line to hold is that one — if it ever grows a control that *changes* a session (kill, resume, rename), the tab has become a feature and the argument is lost.
  - **One array, two renderers would drift.** The pane is built from a `report` structure (sections → labeled rows), and both the DOM and the clipboard text render from it. A copy that could report a different value than the pane it was copied from is worse than no copy — the whole point is that the paste is the reading you were looking at.
  - **Plain text, no code fence:** the panel includes the last prompt verbatim, which can itself contain a fence and would break the block. Labels are padded to a fixed column so a monospace paste reads as the same two columns; the "open ≠ running" note travels with the counts it disambiguates, since whoever reads the paste can't see this pane. `navigator.clipboard.writeText` (the same route as the row menu's *Copy path* — no new preload surface), and a rejected write says **Failed** rather than silently looking like success.
- **Parked, deliberately not built:** `sessions/<pid>.json` is a *file*, so an fs-watch on `~/.claude/sessions/` could eventually replace the 275ms `claude agents --json` subprocess poll entirely. Real, and tempting, but it trades a documented CLI contract for an undocumented file — its own decision, not this one.

## Notes tab (2026-08-27)

A **fourth tab in the pane strip — Terminal | Preview | Session | Notes** — on Claude sessions only: a plain-text scratchpad for what you're keeping in your head about that session. Explicitly **the original Notepad, not an editor**: no markdown, no toolbar, no formatting, no find, no export. Checked against the out-of-scope list and clear of it — the one rule it touches is "no database", which it honours by not having storage of its own.

- **The text is a field on the session**, so it rides the same state JSON as the row's other remembered facts (`todo`, cwd, conversation id). Consequences, both intended: notes **survive a restart** with the session, and they **die when the row is closed** — a note is about *this* session, not about the directory. If they should ever outlive a closed row, that is a different keying (per cwd, or an archive) and its own decision.
- **Written only when non-empty**, and the field is additive/optional on both the main and renderer state types — an empty editor is not state, and no version bump is needed (same rule the `statusRgb`/font fields already follow).
- **Bound straight to the store, no debounce in the renderer.** `saveState` in main already coalesces at 300ms, so a keystroke costs one IPC message and one snapshot map — the same cost the tower-width drag has always paid.
- **Stays mounted and merely hidden between tab switches**, like the terminal and *unlike* Preview/Info. Those two unmount to disarm a watcher; the notepad has nothing to disarm, and a textarea that unmounts loses its **undo history and scroll position** — losing Ctrl+Z by glancing at the terminal is not what a notepad does. Focus follows the tab (the editor is ready to type the moment it is picked), scoped to the focused pane so the other sessions' mounted editors never steal it.
- **Deliberately not built:** markdown rendering, search, export, per-directory or global notes, a tower indicator that a session *has* notes. Flag them rather than build them.

## Relaunch session (2026-09-04)

A **row context-menu item — *Relaunch session*** on Claude rows: end this session's Claude process and bring the **same conversation** straight back up in a fresh one. The row keeps its place in the tower, its colour, its TODO flag and its notes; only the process underneath is new. Why you'd want it: the CLI updated and you want this session on the new build, the TUI is wedged, the environment changed under it — today the only route is close the row and hand-resume, which loses the row and its notes.

- **It is the restart path, aimed at one row.** Every restore already does exactly this to every row: `createSession` with a `resumeId`, spawning the blessed `--resume <id>`. Relaunch reuses that code as-is, so it introduces **no new spawn-line deviation** and nothing new for the fidelity ethos to weigh — the app still runs the unmodified CLI with a flag it already passes. Claude Code has the same idea for its own background sessions: `claude respawn <id>` — *"Restart a background session … so it runs the current Claude Code version"*.
- **Checked against the out-of-scope list and clear of it.** No git, no PR, no kanban, no graph, no theme, no database. It also does not touch the *Session tab's* line — that tab stays read-only; this is the **row menu**, which has always been where a session's lifecycle lives (Duplicate, Rename, Close).
- **The kill and the respawn cannot share a flush — verified, not assumed.** `claude --resume <id>` **refuses while that id is still live**. Measured on 2.1.261: with the session running, `claude --resume <id> -p …` returned `Error: Session <id> is running as a background session (9b1f46e0). Run "claude attach 9b1f46e0" to open it, or "claude stop 9b1f46e0" first to resume it here. Add --fork-session to branch off a copy instead.` — and the same command resumed cleanly, **same id, same conversation**, the moment the process was stopped. (Probed against a background session, the only kind that can be held live without a TTY; the guard is about the id being registered as running, which is the same registry `claude agents --json` reports interactive sessions in.) So a naive splice — new row in, old row out, one Svelte flush — races the old process's death and can land on that error, or on two claudes appending to one transcript.
- **Two steps, joined by the PTY's own exit event.** `relaunchSession` arms the row (`relaunching`) and kills its PTY; the Terminal's existing `onExited` calls `finishRelaunch`, which does the swap. No new preload surface and no timer — the signal that the process is gone is the one the app already receives. A relaunch's exit is **not** the session exiting, so `finishRelaunch` returns whether it handled it and the row is *not* marked `exited` on the way past (`setStatus(_, 'exited')` would clear the TODO flag the row is about to carry across). A row with nothing alive to wait for — a spawn that errored, a process already dead — swaps immediately; relaunching a dead row back into its conversation is the other half of what this is for. No settle timer beyond the exit event, and on purpose: **restore already does kill-then-resume on every restart** (`killAllPtys` terminates the same way), which is the standing evidence that a terminated process frees its id immediately — the registry is keyed on a pid that is gone. If a visual test ever catches the race, the delay gets added *with* that evidence, not ahead of it.
- **The transcript tail is kept, deliberately, where `closeSession` drops it.** The conversation id is unchanged, so the preview cache and main's tail are still the right ones and the resumed process appends to the same file. Dropping them would only buy a re-read of a multi-MB transcript.
- **Offered only when there is a conversation to resume** (`claudeSessionId` set) — a window that lasts from spawn until the PTY answers, milliseconds. Shell rows don't get the item: a shell has no conversation, and "restart my shell" is a close and a new row.
- **Deliberately not built:** relaunch-all, a keyboard shortcut, `--fork-session` ("relaunch as a copy"), and any auto-relaunch on crash. Flag them rather than build them.

## Alternate status detection — the screen scan (2026-09-05)

A **second technique for the status dot, selectable in Settings** (*Status detection: Hooks + poll · Screen*), ported from **[herdr](https://github.com/herdrdev/herdr)** (Apache-2.0, Rust, a terminal runtime for coding agents). Herdr has no hooks — it does not own the spawn line — so its only route to "working / blocked / idle" is *reading the pane*, and it does that with a **prioritised rule set matched against regions of the rendered screen plus the OSC title**, highest priority wins. That is a genuinely different instrument from ours, and it sees things ours cannot. **`ui.statusSource` picks one. Screen became the default on 2026-09-12** (it shipped as Hooks + poll).

**Everything below was captured from Claude Code 2.1.261**, not read off herdr's manifest: a scratch harness spawns `claude` in a real ConPTY (the app's own node-pty), feeds the byte stream into a headless xterm, and dumps the viewport plus the title at each state. The captures are committed as `screens.fixtures.ts` and are what `screen.test.ts` asserts against.

- **Two measured facts decide the design.** (1) **The OSC title alone separates working from not-working** — it leads with a half-circle spinner frame for the whole turn (`◐ Claude Code`, `◑ Glob src and summarize pty.ts`, U+25D0–U+25D3) and with `✳` (U+2733) when the turn is over. We already receive that string; `glyphLead`'s existing star-vs-circle families are the same split, arrived at independently for the cosmetic *Color title glyph* setting. (2) **The title cannot see blocked.** A session parked on a permission dialog still reports `✳ <name>` — the *idle* glyph. A title-only technique would paint it **green**, the one colour that means "nothing wants you". That is why the title's idle rule ranks **250** against the screen's blocked rules at **840–980**, and it is the whole reason the screen scan earns its keep.
- **Herdr's char classes are exactly right for 2.1.261 — verified, not assumed.** The in-progress activity line cycles through precisely the six frames in their class (`✶ ✻ ✽ * ✢ ·`) and is separated from a *finished* line by the ellipsis plus an elapsed-time parenthetical: `✽ Baking… (7s · ↓ 338 tokens)` runs, `✻ Brewed for 2s · done 9:50` does not. The mode footer likewise only means work while it offers the interrupt — `⏸ manual mode on · ← for agents` is idle, `⏵⏵ auto mode on · 1 shell · esc to interrupt` is not.
- **The regions do the hard work, not the wordlists.** The idle input box is the span between the **last two** box borders; a dialog renders under **one**. So while a permission dialog is up there is no prompt box at all, and `❯ 1. Yes` can never be mistaken for the input line — a structural invariant that survives wording changes. Captured on both dialog shapes: the workspace-trust form (`Enter to confirm · Esc to cancel` over `❯ No, exit`) and a tool permission dialog (`Do you want to proceed?` over `❯ 1. Yes`, footer `Esc to cancel · Tab to amend`).
- **No opinion is a first-class answer.** When no rule matches, `screenStatus` returns **null** and the dot **holds its last colour**. Claude Code's TUI moves — herdr versions its manifest per release (`version = "2026.08.31.1"`) and ships a remote update channel precisely because these patterns rot. We are pinning a snapshot with no such channel, so the failure mode is chosen deliberately: **a stale dot, never a confident wrong one.** That is the same lesson the 2026-08-17/19 status rewrite paid for three times.
- **One technique at a time, and the other keeps its bookkeeping.** Selecting *Screen* stops the hooks and the poll from **painting** (`setStatusFromHooks`) but changes nothing else they do: following a `/clear` to its new conversation id, adopting a spawned worktree's cwd, tracking the claude pid, retaining the raw poll entry the Session tab reads. Two channels writing one dot is the disagreement that rewrite removed; it is not coming back as a setting.
- **What the screen technique gives up:** **`delegating`**. Subagents are in-process API calls with no screen presence, so the fourth state is hook-only and a screen-driven dot lands on running or idle instead. What it gains, in exchange, is the three things the hooks cannot see: an **interrupt** (no hook fires on Ctrl+C — the screen simply shows the prompt box again, which also makes the Esc ambiguity of issue #6 moot while this technique is selected), a **`busy` that is really a background shell** (the poll's known blind spot — the screen shows a settled prompt box), and a **missed `Stop`**.
- **Cost:** the buffer is read **only while the technique is selected** (`scanning` gates it in `Terminal.svelte`), throttled to one scan per 250ms per session, reading `rows` lines and running a handful of regexes. A settled session emits no bytes, so it costs nothing at rest.
- **Ported, verified against captures:** `osc_title_working` (1100), `transcript_viewer` (1000), `live_blocked_form`/`bash_permission_prompt`/`generic_permission_prompt` (980/850/840 — one predicate here, they all land on amber), `live_turn_working` (970), `live_prompt_box` (950), `model_picker_menu` (900), `osc_title_idle` (250). **Deliberately not ported**, and recorded in `screen.ts` so the gap is a decision: `btw_overlay_working` (unverifiable here, and it collides with issue #6), `background_agents_working`, `background_mcp_task_working`, `dynamic_workflow_prompt`, `mcp_elicitation_prompt`, `legacy_no_prompt_blocker` (a broad pre-manifest catch-all), and `osc_progress_idle` — **Claude Code 2.1.261 emitted zero OSC 9;4 sequences** across every capture, so that rule would be dead code.

### The ethos call this needs (flagged, not assumed)

The *Session inspector* section above rejected reading the terminal buffer: *"The only routes to it are scraping the terminal buffer (fragile, and it **is** the byte stream)… Both fail the fidelity ethos; rejected."* That ruling was about **replicating Claude's status line**, and it stands — we still render nothing of Claude's UI. This is narrower: a **read** of the rendered grid to colour our own dot, writing nothing, intercepting nothing, steering nothing. It is the same *kind* of observation as the terminal title we already read and already classify by glyph — the title is a piece of that byte stream too.

Still: **it is buffer scraping, and the doc said no once.** So it ships **off by default, behind a named switch**, exactly like Status RGB (**both of those defaults flipped on 2026-09-12** — the switch and everything below it stand, only the starting position moved) — and if the answer is that the ethos means no buffer reads at all regardless of direction, the switch comes out and the investigation stands on its own as the empirical record of how Claude Code 2.1.261 paints its states. **Carlos's call.**

## A second agent: Codex (2026-09-05)

A **third spawn button beside Claude and shell** — `codex` rows in the same tower, same folders, same drag-and-drop, same status dots. Everything about the app that isn't the CLI itself is unchanged and shared; what differs is narrow, recorded, and lives in one place per side of the process boundary (`src/main/cli/index.ts` for the spawn line, `AGENTS` in `sessions.svelte.ts` for the affordances).

**Every fact below was measured against codex-cli 0.153.4** — the CLI's own help, a live ConPTY capture through a headless xterm, and a real rollout written by a session this app spawned.

### The ethos rule this changes — flagged for sign-off

Rule #2 is *"Full-fidelity **Claude Code**"*. Its **substance is unchanged and now applies to both**: the unmodified CLI runs in a real ConPTY, and the app never intercepts, rewrites, or steers the byte stream. What needs generalising is the wording, and one specific: the blessed-deviation list is Claude's (`--session-id`/`--settings`, `--worktree`, `/color` and `/rename` injection). **Codex's list is shorter, not longer** — `codex` or `codex resume <id>`, and nothing else. No flags of ours, no settings file, no injected typing. If anything the second agent is the *stricter* citizen.

**Signed off and rewritten 2026-09-10.** `CLAUDE.md`'s rule #2 now reads *"Full-fidelity agent CLI"*, carries the two deviation lists separately (Claude's, then Codex's shorter one), names `src/main/cli/` as the single home of every spawn line, and separates the app-wide keys and the out-of-band observation channels — the poll, the rollout and session index, the transcripts, the title and the screen buffer — from anything that touches a spawn line, which none of them do.

### Where the two differ, and what each difference cost

| | Claude Code | Codex 0.153.4 |
| --- | --- | --- |
| Conversation id | **pinned** at spawn (`--session-id`) | **minted by codex** — discovered afterwards |
| Resume | `--resume <id>` | `codex resume <id>` |
| Transcript | `~/.claude/projects/<enc-cwd>/<id>.jsonl` | `~/.codex/sessions/YYYY/MM/DD/rollout-<ts>-<id>.jsonl` |
| Status | hooks + poll, two channels | **the terminal title**, one channel |
| Terminal title | the conversation's name | the working **directory's** basename |
| Fresh worktree at spawn | `--worktree` | no such flag |

- **Identity is discovered, not pinned — and the join is exact.** Codex has no `--session-id`, so a codex row spawns with no conversation id and learns it a beat later. The rollout's first record settles it beyond guessing: `payload.cwd` is the directory we spawned in verbatim, `payload.source` is `"cli"` (the desktop app writes `"vscode"`), and `payload.originator` is `"codex-tui"` (the desktop app writes `"Codex Desktop"`). cwd + source + a creation time at or after our spawn is three independent signals, which is what makes it safe to adopt — including against the user's own codex running in another window. Until it lands the row is a perfectly good terminal with no preview and nothing to resume; that window is normally under a second and is why the id arrives as an event rather than being a precondition.
- **Status needs no new machinery at all, and that is the happy finding.** Measured: the title leads with a braille spinner for the whole turn (`⠹ my-project`) and is bare when it isn't (`my-project`); herdr's manifest adds `Action Required` for blocked. **Codex's title carries all three states**, where Claude's cannot see blocked at all. So codex reuses the screen technique already in the app (`screen.ts`) with herdr's codex rule set — no hook server, no poll, no `--settings`. The screen rules below the title (`• Working (39s • esc to interrupt)`, the trust prompt, `allow command?`) are fallbacks.
  - **Consequence, stated plainly:** for Claude the screen scan is opt-in because the hooks are better; **codex has no other channel, so its dot always uses it.** The *Status detection* setting therefore picks a technique only where there is a choice — it governs Claude. That asymmetry is deliberate and is the honest reading of "one technique at a time".
- **`claude agents --json` stays claude-only.** The poller is gated on a live *Claude* PTY, so a tower of codex rows never spawns it. `codex agents` exists but is an interactive browser with no JSON mode, so there is no floor to borrow; codex doesn't need one, because its title never lies the way the poll's `busy` does.
- **Preview reached parity; the Session tab did not.** The rollout is JSONL like Claude's, so the tail machinery — offset, remainder, the missed-event backstop — is shared unchanged and only the **fold** is per-agent (`parse` is now a constructor argument). Codex's fold keeps `response_item`/`message` for `user` and `assistant` and drops everything else: `function_call`, `function_call_output`, `event_msg`, `token_usage_record`, `world_state`, `turn_context`. Two codex-specific drops, both measured: the **`developer` role** is the skills catalogue and sandbox policy — the system prompt by another name — and **`reasoning` records are encrypted** with an empty summary, so there is no thinking to show. Codex also opens every session with an `<environment_context>` block sent *as the user*, which the fold drops by shape (one XML-ish element start to finish) rather than by role. **The Session tab stays Claude-only**: it reads `~/.claude/sessions/<pid>.json` and folds a Claude transcript for its numbers, none of which exist here, and a mostly-empty instrument panel is worse than no tab.
- **The name comes from the session index, because the title can't supply it.** Codex titles the window with the working directory, so every codex row in one folder would read the same word — fatal for the app's core use case. `~/.codex/session_index.jsonl` is a small append-only `{id, thread_name, updated_at}` log; the row takes `thread_name` from it. Codex names a thread a turn or two in, so it is polled briefly (3s, for three minutes after discovery) and then left alone — names settle early, and a permanent poll per row is the sort of background cost the app avoids elsewhere. A rename after that window keeps the old label.
- **Capabilities, not kind checks.** The UI asks what a row *can do* rather than which CLI it is, so a missing capability hides an affordance instead of offering one that silently fails. Codex: no `--worktree` (the repo card's fresh-worktree button stays Claude's — and we will not shell out to git ourselves, which the out-of-scope list forbids outright), no `/rename` or `/color` injection (unverified on this build, and typing a command the TUI doesn't understand would put stray text in the composer), no Session tab. It **does** get Terminal, Preview, Notes, the status dot, TODO, folders, drag-and-drop, close, duplicate, and **Relaunch** — `codex resume <id>` makes that one work unchanged.
- **Deliberately not built:** the codex **app-server daemon**. It ships a real JSON-RPC protocol with `TurnStarted` / `TurnCompleted` / `ThreadStatusChanged` and explicit approval requests — the true analogue of Claude's hooks, and richer. It is the obvious upgrade if the title ever stops being enough, and it is not worth a socket client and a 79-notification protocol while one string already answers the question. Also parked: renaming the in-memory `claudeSessionId` field to something agent-neutral (it now holds either agent's conversation id). Worth doing, but as its own mechanical commit — the persisted key must keep its name either way, or every existing state file loses its sessions.

## Session archive (2026-09-09)

A **row context-menu item — *Archive session*** (both agents and shells), plus a foldable **archive section at the bottom of each project card**. Purely presentational: an archived session keeps running, keeps its status colour, its TODO flag, its notes, its tabs and its place in the focus order. The only things that change are where its row sits and how its dot is drawn. It solves the problem closing a row solves badly — a long-lived session you are done glancing at but not done with, cluttering the card you are actually working in.

- **The archive belongs to the card, not to the tower.** Considered and rejected: one global archive at the bottom of the whole tower. It declutters more and needs exactly one separator, but an archived row would leave its card, lose the repo colour tab and the branch it ran on, and a card whose sessions were all archived would vanish from the tower along with its spawn buttons. A per-branch archive was rejected too — most context kept, but a separator per branch is the least decluttering of the three shapes. Per card: archived rows sit below every branch row, keep the card's colour, and one separator serves the whole project.
- **The separator is the fold toggle**, exactly like a card's name (issue #5): a hairline across the card carrying a muted count, clicked to fold and unfold. It renders only when the card actually holds archived sessions, so a tower with nothing archived looks precisely as it does today — with the one exception below, a drag in flight. **Revised 2026-09-09:** the count lost the word *archived* to a Material `archive` glyph in front of the number, and the pair moved from the LEFT end of the rule to the right. Two reasons, both about the card's left edge: every row lines its dot and type icon up on fixed grid tracks there, and a label sitting in that margin was the one thing crossing them; and the glyph says "archive" in the space a word needed, so the count can be a bare number.
- **It folds by default**, which inverts the card's own rule (`collapsedGroups` stores collapsed keys, absent = expanded; `expandedArchives` stores expanded ones, absent = folded). Deliberate: the whole point of archiving a row is to get it out of the way, and a section that opens itself on the first archive would not. The count is what stops that reading as a close.
- **Archived dots are drawn as a ring, not a disc** — same colour, hollow. The status classes now set a `--dot-fill` custom property instead of painting `background` directly, so one `.dot.archived` rule turns every state inside out — the neutral shell tint and the blue TODO pulse included — without knowing any of their colours.
- **The roll-up dot on a collapsed card still counts archived sessions.** Tempting to exclude them — they are "out of the way" — but that would make a visual feature a behavioural one: a folded card would stop telling you an archived session is blocked on a permission dialog. Archiving hides a row; it does not silence it. **Revised 2026-09-09:** it now says so, too. The winning session's own `archived` flag rides along and the roll-up is drawn **hollow** for it, reusing the same `.dot.archived` rule the rows use — so a folded card still shouts amber for a blocked archived session while the ring says where to look, instead of sending you to unfold a card whose every visible row is calm.
- **A filter reveals the archive.** While the tower filter is active and a card's archive holds a match, the section shows regardless of its fold state — a search that cannot find a session you know exists is a bug, not decluttering. The stored fold state is never written by this, so it comes back when the filter clears.
- **`archived` is a persisted field on the session**, exactly the shape `todo` already has: written only when true, additive on both state types, no version bump. It survives a restart and dies when the row is closed, which is right — the archive is about *this* session, not about the directory.
- **Checked against the out-of-scope list and clear of it.** No git, no PR, no kanban, no graph, no theme, no database. No spawn-line change and nothing near the PTY: the CLI cannot tell it has been archived.
- **Placement, revised 2026-09-09.** The original rule was that the row keeps its index, so unarchiving put it back exactly where it had been. That reads well in a two-row card and badly everywhere else: the row rejoins its list in the *middle*, at a position nobody chose and nothing marks. Each direction now re-seats the row at the near end of the list it joins — archiving to the **top of the archive** (what you just filed is what you might undo, and it is the row your eye just left), unarchiving to the **bottom of the live list** (a row coming back is the oldest one, not something that jumps ahead of sessions you have been driving). Because a card's archive spans every cwd in its group and its live lists are per branch, the two ends are measured differently: the archive end against the whole **group**, the live end against the row's own **cwd**. A row whose far side is empty has no near end to travel to and simply stays where it sits.
- **Dragging across the divider archives and unarchives (2026-09-09).** The tower's session drag already reordered rows within a directory; it now also crosses the divider, which is the direct-manipulation half of the context menu. Two targets. **A row in the other section** takes the drop and hands the dragged row its own `archived` flag on the way past — a drag names a position, so unlike the menu it does not snap to an end. **The divider itself** is the boundary, so a drop on it simply crosses: whichever side the row was on it ends up on the other, at that section's near end. The divider is the only one of the two that works when the far side is empty, which is why it **reveals itself for the length of a drag** inside a card that has no archive yet — otherwise the first row of a card could never be archived by dragging. The store keeps two guards, and the drop highlight mirrors them exactly so it never promises a move that will not happen: both rows must be in the same **card** (that is as far as a drag reaches), and a **live** target must additionally share the **cwd**, because live rows are drawn per branch and a row from another worktree would vanish back into its own list. The archive is one flat list per card, so any row of the card can land anywhere in it.
- **Deliberately not built:** archive-all / unarchive-all, a keyboard shortcut, auto-archiving by idleness or age, an archive that outlives a closed row, a tower-wide archive count, and sorting inside the section (the section is ordered by the same drag that orders every other list). Flag them rather than build them.

## Per-pane zoom (2026-09-09)

**Ctrl+wheel over a pane sizes that pane's text**, independently of the other four: the tower, the terminal, the Preview tab, the Session tab and the Notes tab. They are read at different distances — the tower is glanced at, a transcript is read, the terminal is worked in — and one window-wide size can only ever be a compromise between them.

- **Steps, not factors, and a step is HALF a window-zoom level (halved 2026-09-09).** ±20% is the right size for a keypress and too coarse for a wheel, where one notch of it overshoots what you were aiming at; halved it is ~9.5% a notch, perceptible but small enough to land on. The halves are deliberate rather than some independent percentage: **two notches are exactly one window-zoom level**, so every even step still lands precisely on a size Ctrl+= could have produced, and the clamp is doubled so the reachable extent is identical to the window's. Persisted (`paneZoom`, additive/optional, written only for panes actually moved off 0 and clamped again on the way back in — the state file is external data). No migration for the unit change, per the pre-1.0 no-compat policy: a level stored before the halving reads as half its old size, which the wheel fixes in two notches — cheaper than the factory reset a `version` bump would cost for something cosmetic.
- **Ctrl+=/−/0 still means "size the app", and resets every pane to 0.** Main sends a `zoom:sync` on each press and the renderer drops the offsets, so the window zoom stays legible as a single control instead of becoming one more thing layered under five others. That, not the per-pane keys, is why there are no per-pane keyboard shortcuts: the wheel gesture is aimed at a pane, and a key press is not.
- **CSS `zoom` for the four chrome panes.** One declaration scales the text and every px in the pane's chrome with it, which is what makes it tractable for panes whose sizes are all in px — the alternative was rewriting every hard-coded size in the app as an em. Verified empirically in this Electron (43.1.0 / standardized `zoom`): a zoomed child's `width: 100%` / `height: 100%` still fills its unzoomed parent exactly, and `getBoundingClientRect` reports visual coordinates, so menu positioning off a zoomed button needs no correction. The one thing `zoom` also scales is the element's own `width`, so the **tower's width is pre-divided by its factor** — the splitter stores the width the user dragged to, in real screen px, and it must not move when the text does.
- **The terminal takes a font SCALE instead**, multiplying xterm's own `fontSize`. Its size change has to re-measure the cell, reflow the grid and resize the PTY — that is what Ctrl+wheel does in Windows Terminal, and a scaled canvas would just be a bigger picture of the old grid. Not a fidelity deviation: the CLI sees an ordinary terminal resize, the same one dragging the splitter already sends.
- **Bound in the capture phase.** The terminal and the scrolling panes already own the wheel, so the handler stops the event on the way down — otherwise a zoom gesture would also scroll whatever it was aimed at. `preventDefault` additionally stops Chromium's own ctrl+wheel page zoom, which would fight main's window zoom. Any other modifier is left entirely alone.

## The preview's file blocks are tabbed and foldable (2026-09-09)

The code Claude writes reaches the preview as a fenced block with the file name above it (`Write` shows content, `Edit`/`MultiEdit` a +/− diff). The name was a separate line of markdown, so it read as a caption floating above an unrelated box. It is now a **tab welded to the top-left of the block**, and the same tab folds it.

- **The name rides in the fence's info string** as `title="..."` — the Docusaurus/Shiki convention — rather than as a paragraph above the fence, because a paragraph is exactly what it stopped being. Quoted, so a name with spaces survives; a double quote in the name is dropped rather than escaped, which costs nothing (no Windows path can contain one) and keeps the info string parseable by a plain `[^"]*`.
- **`<details>` + `<summary>`, not script.** Preview content is untrusted and sanitized, so the fold has to be native: DOMPurify passes `details`/`summary` (verified), and no behaviour is injected into rendered markup.
- **Folded by default.** The preview is for reading the conversation, and a file listing is the one thing in it that can run to hundreds of lines — expanded, a single `Write` buries the prose either side of it. The tab still says what was written, so nothing is hidden that the reader has to go looking for, and the code is one click away when it is what they came for.
- **Anything else falls through untouched.** A fence in Claude's own prose has no title, so it renders exactly as it always did; a `diff` fence without one still gets the per-line tint (issue #1). The renderer only takes over when a block is one of ours.

## The Settings panel (2026-09-10)

Settings was a **menu that had grown into a dialog**: one 260px column of twenty-three near-identical rows — three theme radios, three checkboxes, two detection radios, then fifteen font radios in three groups — separated by hairlines. Every control had the same shape, so the panel carried no information about what any of them did, and finding one meant reading all of them. Same controls, same names, same state keys; **only the layout changed**.

- **The panel stops borrowing the popup menus' row language.** `.menu-item`/`.menu-label`/`.menu-divider` are how the context menus look, and a menu is a list of things to *do*. A settings panel is a set of states to *read*, and dressing the second as the first is what produced the twenty-three rows. It now has its own idiom: 400px wide, three sections under the Session tab's own uppercase headings (the app already had a "group of labelled facts" shape — this is that shape), and a **label-left / control-right grid** so every control starts at the same x and the eye runs down one column.
- **Each control has the shape of the choice it makes.** A **segmented control** for one-of-two-or-three (Theme, with a glyph per mode; Detection), where showing the options costs less than hiding them and the set reads as a single control. A **switch** for on/off, because a checkbox glyph in a menu row reads as "an item you can tick" rather than as state. A **picker** for one-of-five.
- **The font pickers preview their own faces**, which the radio lists already did and is the one thing worth keeping: the current face is rendered *in* that face, and unfolding shows all five as chips, each its own specimen. A font name set in the app's font tells you nothing about the font. **Unfolds in place, not into a popup menu**: the panel is already a dialog with a backdrop, and a second layer over it would need its own backdrop and z-index for no gain. **One open at a time** (`openFont` holds the row, not a flag per row), so the panel can never grow by three lists at once, and it folds when the panel closes.
- **The Detection hint came out of a `title` attribute** and onto the panel, under the control, changing with the selection — it explains what *is* selected instead of making you hover both to find out. It also states the asymmetry the setting can't show on its own: Claude rows only, because a Codex row has no second technique to choose between.
- **A close button.** With the panel non-modal (below) it is the only pointer way out — Escape is the other — rather than the affordance a dimmed modal is expected to have.
- **Non-modal and draggable (2026-09-11).** The backdrop is **gone**: nothing dims, nothing is blocked, and a click on the tower goes to the tower. Every control in the panel changes the app *behind* it — the card washes and edge most of all — so a panel that dims what it is changing is the wrong shape for the job; you now open it, drag it clear of the rows you are watching, and dial a setting while the tower answers underneath. The **header is the drag handle** (a title bar, where anyone reaches for it; `cursor: move`, `user-select: none`, and a click on the close button is not a drag), the position is clamped to the window so the handle can never be dragged out of reach, and it is tracked in viewport px with the centring `transform` dropped once a drag starts. **The position is deliberately not persisted and resets on close:** it opens centred every time, so the panel can never be hunted for in a corner you left it in a week ago. Moving it is a gesture for right now, not a preference. Escape still closes it (after an open font picker, which is the innermost thing Escape can mean).
- **Deliberately not done:** a left-hand section nav (four sections don't earn a second column), a live sample line per font (the chip *is* the specimen), search, per-setting reset, and renaming any setting — "Status RGB" and the rest keep their names so the docs' vocabulary stays valid. The ask was the layout.

## macOS: Windows first, macOS in progress (2026-09-12)

**The stance, settled today.** Agent Race Control is **Windows first, macOS in progress**. Windows is what it is developed on, tested on, packaged for and screenshotted on; macOS is a second host the code no longer *refuses*, but that ships no artifact yet. "Native Windows" is retired as a **scope** claim and kept as a **priority** one: a macOS change that costs Windows anything is not taken. The fidelity rule reads the same on either host — if it works in the user's own terminal (Windows Terminal there, Terminal.app/iTerm here) and not in Agent Race Control, it's our bug.

**Where it came from.** Issue #8: a sibling Electron + node-pty app at LEGO Digital Play (Brick Developer Hub) lifted this repo's terminal module — `bash.ts` essentially verbatim, the pty registry and xterm component as copies — then grew macOS as a second first-class host and sent the port back as measured notes. PR #9 merged **the mechanical half** on 2026-09-12: four hard blockers, plus the first CI this repo has ever had. The measuring machine is **darwin 25.6.0 arm64, `$SHELL = /bin/zsh`, Electron 42.5.2**; every claim in the issue states whether it is measured there or marked inference, and nothing was adopted from documentation alone. The honest limit **at merge time** was that nobody had run Agent Race Control on a Mac — the macOS behaviours were measured, their mapping onto this code was not. That held for about three hours; see *First run on a Mac* below.

### What landed (PR #9)

- **The shell is dispatched around `bash.ts`, not rewritten (`src/main/shell.ts`).** The Windows branch is `findGitBash()` unchanged, because its reasoning is intricate — never PATH-resolve `bash.exe`, the WSL stub and the legacy launcher both shadow it — and worth keeping reviewable as the thing it always was. This **amends the "spawn Git Bash, non-negotiable" decision** in *Technical specifics*: it is non-negotiable **on Windows**, and off Windows there is no Git Bash to spawn.
- **POSIX gets the user's login shell (`$SHELL`), not a fixed `/bin/bash`.** Measured: on that Mac the agent CLI reached PATH **only** through `.zshrc`, with no `.bash_profile` or `.bashrc` on the box at all — a hardcoded bash opens a terminal that cannot see the user's own toolchain, which is the fidelity rule broken at the first keystroke. `$SHELL` is trusted only when **absolute and existing** (a relative value resolves against this process's cwd, and a stale one fails inside node-pty as opaque noise), falling back to `/bin/zsh` on darwin and `/bin/bash` elsewhere; the result is a discriminated union, so a caller cannot read a shell out of a failure. Dialect parity was considered and rejected: nothing here ever scripts the shell, and `cli/index.ts`'s `exec claude …` line is POSIX-portable as written — so **the agent spawn line is byte-identical on both hosts and `cli/` was not touched**.
- **node-pty's darwin `spawn-helper` ships without its execute bit**, and the symptom is a **blank pane with no error** — there is nothing to print, because the shell never started. Verified against the tarball (`npm pack node-pty@1.1.0`), not inferred: `prebuilds/darwin-arm64/spawn-helper` is `-rw-r--r--`, and neither the install nor the postinstall script chmods it. `scripts/fix-pty-perms.mjs` runs **ahead of `dist`**, not as a postinstall, because electron-builder copies the mode it finds in `node_modules` — chmod after packaging and the `.app` ships with blank terminals for every user. Upstream fixed it in 1.2.0-beta; **delete the script when node-pty is bumped past 1.1.0**, and its "nothing to do" branch is what tells you it is safe to.
- **This process's PATH is repaired before anything can spawn (`src/main/login-path.ts`, awaited first in `whenReady`).** Two bugs of one shape. **macOS:** an app launched from Finder or the Dock inherits **launchd's** environment — `launchctl getenv PATH` is empty, so it gets launchd's default `/usr/bin:/bin:/usr/sbin:/sbin` with no Homebrew, no version-manager shim, no `~/.local/bin`. This appears only in the arrangement nobody develops in; a dev launch from a terminal inherits the terminal's PATH and shows none of it. **Windows:** a process inherits its **parent's** environment block, so anything launched from a shell that started before a PATH-changing install keeps the old PATH for its whole life — measured right after installing a CLI, the persisted machine PATH held its directory and the running app's did not, which is why "just restart it" is not the fix. One repair covers every later caller (`git.ts`'s bare `execFile('git', …)`, and the absolute `claude` path `agents.ts` resolves, whose own shebang has to find `node` on *this* process's PATH). Three details are load-bearing: the capture is **`-l -i`**, because an rc file sourced only for *interactive* shells is where a version manager puts the CLI and a login-only capture returns a PATH without it **and looks like it worked**; the output is **fenced with sentinels**, because an interactive shell prints whatever its rc files print; and the *question* is asked in a **POSIX-compatible shell chosen by basename**, because in fish `$PATH` is a list that `"$PATH"` joins with spaces and nushell does not expand it at all — either returns something non-empty that parses as one bogus entry, which is the bug unfixed and reported as fixed. Failure is silent and cannot make things worse: the merge is a **union**, so nothing reachable before becomes unreachable. The PTYs were never the symptom — they start a login shell and derive their own.
- **`cygpath` is MSYS-only.** The `claude` resolve in `agents.ts` converted its answer with `cygpath -w`, which does not exist outside MSYS/Cygwin: on macOS the command fails, `claudePath` caches `null`, and **agent polling is silently off forever** — that failure path is deliberately never fatal, which is exactly what hides it. On POSIX `command -v claude` already answers with a spawnable absolute path, so there is nothing to convert. The resolve now also asks the **same shell, with the same args**, that `pty.ts` spawns, through the shared `askShell`.
- **CI, for the first time (`.github/workflows/gates.yml`).** `typecheck` + `test` on `windows-latest` and `macos-latest` — nothing here proved this built on *any* platform before, Windows included. `npm ci --ignore-scripts` is deliberate: electron's postinstall downloads a ~100MB `dist/` neither gate needs, and node-pty declares an install script this repo's own rule says must never rebuild. `fix-pty-perms` runs on both hosts so the script is exercised on both. `.nvmrc` pins the **major** (24), so the runner and the developer read one number. **Deliberately not here:** anything that launches Electron. The one worth adding is a smoke test that boots the app and spawns a single PTY — it covers both failures that make this app useless on a Mac — but it needs the Electron binary and a window server, so it is a separate job.

### The cost, stated plainly

An independent adversarial review of the branch found **three Windows regressions in a PR whose whole promise was to leave Windows alone**, and all three are one mistake: a change reasoned about on the Mac whose Windows form was asserted rather than measured. They are recorded because the pattern will recur on every later macOS change.

- **`-i` poisoned the `claude` resolve.** Interactive unlocks every rc block gated on `$-`, and Git for Windows has one that prints a post-upgrade warning **to stdout** (`printf`, no `1>&2`; `test -t 1` is false under `execFile`). `agents.ts` took stdout as the binary's path — so upgrade Git, launch, and `claudePath` becomes a warning banner with a path glued on the end, every `execFile` of it ENOENTs, and **the tower shows no status for the entire session**. It is cached, and the `.warning.once` file is deleted on read, so it is gone by the next launch: silent, cached, intermittent. The guard already existed 30 lines away in `login-path.ts`, so the fencing moved into `shell.ts` as **`askShell`** — one place that knows how to ask the user's shell a question and trust the answer, and it keeps "the shell ran and said nothing" distinct from "the shell would not start", which `agents.ts` needs because it caches its answer forever.
- **The registry PATH was prepended, and reordered all of it.** "It can only ever *add* an entry" is true of membership, and PATH order is resolution order. Measured against a real 49-entry PATH: **0 entries lost, 49 of 49 ranks changed**, and bare `git` moved from `mingw64\bin\git.exe` to `cmd\git.exe`. `git.ts` runs a bare `execFile('git', …)`, and Git Bash defaults `MSYS2_PATH_TYPE` to `inherit`, so **every terminal the app spawns** would have inherited the reordering, quietly demoting an activated venv, conda or fnm prefix. Windows now **appends** — the stale block is a subset of the persisted PATH, so missing entries get added and present ones keep their rank. POSIX keeps captured-first, and the asymmetry is deliberate: launchd's PATH is not a stale copy of the user's, it is four system directories that were never their order at all.
- **`fix-pty-perms` was not a no-op on Windows.** node-pty ships **every** prebuild directory in one tarball on every host — `darwin-arm64`, `darwin-x64`, `win32-arm64`, `win32-x64`, all present on this Windows install — so the script chmodded two files this host never spawns and printed a success message about them, and it made the "nothing to do" branch (the very signal that node-pty has been bumped and the script can go) unreachable here. It exits early on win32 now.

One smaller fix rode along: a stray `%` in a Windows directory name could pair with the next `%VAR%` and swallow the expansion. Mild, since the union keeps the process's real entry either way, but it put a junk directory in PATH.

### First run on a Mac (2026-09-12, same day)

Reported on #8 by a second pair of hands on **macOS 26.5.1 arm64, Electron 43.1.0, Node 26, `$SHELL = /bin/zsh`**, against `836ea02`. **It works.** A shell row comes up as `zsh -l -i` in the repo with its prompt; a Claude row comes up as the real Claude Code TUI sitting on its trust prompt, with the row's dot correctly **amber**; the repo card grouped the cwd under `agent-race-control` on `main`, so `git.ts` needed nothing at all; `[arc] PATH repaired: …` logged at startup; no renderer errors. B1 and the login-PATH work are now measured on a **second** machine rather than mapped onto this code from a sibling app.

**The gap the notes could not have caught: `npm run dev` never ran the chmod.** Keeping it an explicit script called from `dist` is right, and it is what merged — but **dev is how a Mac first meets this app**, and a fresh `npm install` there leaves `prebuilds/darwin-arm64/spawn-helper` at `-rw-r--r--`. So `git clone && npm install && npm run dev` reproduced **B2 in full**: blank pane, no error, nothing to search for. Fixed by chaining `fix-pty-perms` into **every script that starts Electron** — `dev`, `preview`, `screenshots`, and the two `dist` scripts that already had it — rather than into `dev` alone, because the failure has the same shape through any of those doors and the script is a no-op on Windows by construction. Still **not a postinstall**, for the reason already recorded: `--ignore-scripts` is this repo's own rule for node-pty and CI uses it, so an install hook is the one place the chmod could silently not run.

**`TERM_SESSION_ID` now joins the env scrub.** Terminal.app and iTerm set it per tab, and `/etc/zshrc_Apple_Terminal` keys zsh's session save/restore on it — so when `pty.ts`'s deliberate full-env passthrough carries the *launching* terminal's id into every pane, each one "restores" a session it does not own and then fails to delete the file: `Restored session: …` followed by `rm: ~/.zsh_sessions/<uuid>.session: No such file or directory`, on every pane. Cosmetic and dev-only (a `.app` from Finder inherits no terminal's id), and exactly the same shape as the `CLAUDECODE` scrub that is already there: **fidelity is a fresh terminal, not a child of whatever launched the app.** Unverified from Windows, where the variable does not exist and the delete is a no-op — it wants a confirming run on the Mac.

**Still untested there:** Codex rows (not installed on that machine), and the whole of the macOS chrome below.

### Deliberately not done yet

The other half of #8, all still open:

- **`window-all-closed` quits, and there is no `activate` handler** — the two lifecycle rules a Mac app is expected to follow.
- **`Menu.setApplicationMenu(null)` leaves a Mac with no Cmd+Q and no paste.** The nicest finding in the port: macOS accelerators are **Cmd**-based, and Cmd is not a modifier any TUI reads, so the zero-shadow rule and a normal Mac menu are **not in conflict** — the menu can come back on darwin only, without touching Windows.
- **No macOS packaging target at all** — electron-builder is `win` only, so there is nothing to download, and no signing/notarisation story to go with it.
- **Zoom is Ctrl-only and clipboard is Ctrl+Shift+C/V**, both explicitly rejecting `metaKey`.
- **The font stacks are Windows-native** and the default terminal font id names a Windows face; `ui-monospace, "SF Mono", Menlo` and `-apple-system, system-ui` are the portable fallbacks.

Each is small on its own, and none is worth doing blind — but the Mac run has now happened, so they are no longer blind. **The chrome pass is the next real step**, and it is one pass: the lifecycle handlers, a darwin-only menu, and `metaKey` alongside `ctrlKey` in the zoom and clipboard guards. Packaging comes after it, because there is no point shipping a `.app` that cannot paste. A Codex row on a Mac is still unmeasured.

## Packaging (post-v1, settled 2026-07-13)

Ship a real Windows app without growing the stack (**Windows only** — there is no macOS target yet, see the macOS section): **electron-builder** (26.15.3, devDep, verified against the registry) packaging the electron-vite `out/` build into `dist/` (gitignored).

- **Two artifacts (portable added 2026-07-15, reversing the original NSIS-only call):**

## Trailer (2026-07-19, rebuilt 2026-09-10)

A **60s feature trailer** rendered with Motion Canvas. **Eight beats**, one per thing worth knowing: the name → the timing tower and its three session types → the status dot changing colour → the fidelity rule → the four pane tabs → the worktree workflow → settings and the session menu → what survives a restart. The rebuild exists because the six-beat original predated Codex, the pane tabs, the archive, per-pane zoom and the Settings panel — a trailer is documentation, and it had gone as stale as the docs had.

- **Length is set by reading time, not by a round number** (2026-09-10): the first cut ran 30s and was too fast to read at a glance, 45s was still tight, 60s was comfortable, and it settled at **55s**. Every pass moved the holds and left the transitions alone — it is the time text spends still on screen that changed, never the speed of the motion.
- **A beat's length is its word count, not its turn.** The 55s pass stopped dividing the budget evenly and started dividing it by how much each beat asks you to read — the pane tabs carry the most words and now run longest, the worktree beat carries fewer than its three card states suggested and gave time back, and the two title cards, which are a wordmark and one line each, are the shortest things in the film. Screenshots buy a beat a little time on top of its words, because a frame has to be looked at as well as read.
- **The two title cards carry no rule** (2026-09-10): an accent bar sat between the wordmark and the line under it at both ends. The wordmark is already the graphic on those cards, so a bar across the middle of one was furniture rather than hierarchy, and the accent now appears only where it means something — the eyebrow tick and a card's folder stripe.
- **`trailer/` is a standalone subproject** — own `package.json` (Motion Canvas 3.17.2 pins Vite 5; the app is on Vite 7), never part of the app's dependency tree or build. Same arm's-length rule as the screenshot harness: dev tooling, zero app code touched.
- **The footage is the DARK screenshots** (2026-09-10, reversing the original light-on-dark choice). The canvas is `#0d1117`, so a light window pasted onto it read as an inserted photograph rather than as the product. Every shot now gets a hairline border and a deep soft shadow instead — that, not contrast, is what separates a dark frame from the dark ground. Scenes import `images/arc-*-dark.png` directly (a `server.fs.allow` reach-up, no copies); rerunning `npm run screenshots` then re-rendering refreshes the footage.
- **Nothing is scaled far past 1:1.** The doc images are 1× captures and a blow-up shows it, so the two full-window shots sit at 0.8 and the small menu crops top out around 1.5. That ceiling is why the beats are composed around large type with the UI as evidence beside it, rather than around magnified UI.
- **Two transitions, deliberately only two.** `reveal` — opacity plus a ~24px lift on easeOutQuint, leaving the same way — carries every title, list and screenshot; the masked `rise` is reserved for the wordmark, the only thing that uses it, twice. No overshoot, no bounce, nothing springs. The type scale is three sizes: a tracked mono eyebrow names the beat, an Inter 600 headline makes the claim, muted body qualifies it.
- **The status beat is drawn, not screenshotted.** Its whole point is the dot changing colour, which a still cannot show, so that one card is redrawn natively in the app's own geometry and palette and its dots tween green → red → amber → green under the three headline lines. **Each of those lines hangs its own dot in the margin beside it** — naming a colour in words and not showing it was the one thing this beat could not afford. Everything else on screen in the trailer is a real capture.
- **The three session-type marks are the app's own geometry** (`ICONS` in `App.svelte`) inlined as data-URI SVG rather than cropped out of a shot, so they stay vector-crisp at any size. The root `<svg>` needs an explicit pixel size: an `<img>` rasterizes an SVG at its NATURAL size, so a 24-unit viewBox blurs at 40px without it.
- **The worktree beat gives all three of its shots ONE slot** and crossfades them in place — naming field → the branch rows it produced → the reopen menu. Every one of them is the same `pitwall` card, so side by side they read as the same picture three times; in one slot they read as the card changing, which is what actually happens.
- **The Settings shot is cropped to the panel** (`SETTINGS_PANEL` in `lib.tsx`, measured off the pixels). The capture keeps the dimmed app content behind the modal, which at trailer size reads as noise around it rather than as depth.
- **Rendering is automated** (`trailer/render.mjs`): playwright drives the Motion Canvas editor in a real browser — same pattern as the screenshot harness — clicks Render, waits for the ffmpeg exporter to write `trailer/output/`. The output dir and `node_modules/` are gitignored; where the finished mp4 lives (committed or released) is Carlos's call. **Iterating on layout is a half-scale 20fps render plus `ffmpeg -ss` frame pulls**, not a full one — the editor has no frame-grab API worth driving.
- **`render.mjs` preloads every face the scenes use**, Inter 600 added with the rebuild. Canvas `measureText` does not trigger `@font-face` fetches, so an unloaded weight makes the first scene cache fallback metrics.
- **The trailer titles use the wordmark** (see below) and its `appIcon()` shows the real `arc.png` (same fs.allow reach-up as the screenshots, `smoothing={false}` for crisp pixels, sizes snapped to multiples of 16 — intro 208, outro 192), a solid #ff9747 tile, exactly what the taskbar shows — no hand-copied tile drawing.
